# FastSync engine notes

The long per-module notes that used to sit in `AGENTS.md` (moved verbatim). Read the part for the module you change; `AGENTS.md` has the short rules.

- `decide.rs`: the pure three-way compare (local, remote, last synced) -> action; conflict names; delete guard. Exhaustively unit-tested. Change it only with a test for the new case.
- **Same bytes, other times:** `decide` only sees size + mtime, so `run()` turns a `Conflict` into `Adopt` when sizes match and `Remote::same_content` proves equal content. `RcloneRemote` does that with the hash the listing carries (`Item.hash`: first of md5, sha1, quickxor, dropbox, sha256; `showHash` on `list`/`stat`) against `Rclone::local_hash` (rclone hashes the local file). No hash (MEGA) = false = both copies kept. **A hash check that fails is not "different":** `Remote::compare` (default = `same_content`) returns `Err` when the call fails (`Rclone::local_hash` is a `Result`: an unreadable or vanished file, rclone busy) and `Ok(false)` for no hash; `adopt_identical` turns an `Err` into `Action::None` plus a "could not compare, will retry" error (so the normal retry runs) instead of a conflict copy of identical bytes. **The same check runs on a plain `Upload` over an existing cloud file of the same size** (only the local stamp changed: a `touch`, another instance writing the same bytes; seen as 129 needless uploads after two instances shared one folder): equal hashes make it `Adopt`; there an `Err` or no hash (MEGA) just leaves the `Upload`, never an error. Costs one local read of each such file, so a local file over `UPLOAD_COMPARE_MAX` (256 MiB, `pair.rs`) is not checked (a database or VM image edited in place would otherwise be read in full, holding the run's transfers back, at every edit and retry). `pair_moves`/`pair_copies` still use the plain `same_content`: there a wrong "no" only costs a download. Tested through real rclone in `rclone_local.rs`; not yet tried against the real OneDrive/Drive/Dropbox.
- **Which copy gets the `(conflict)` name:** the older by mtime (`exec`, `Action::Conflict`). A local file newer than the cloud's by more than `NEWER_BY_MS` (2 s: providers keep whole seconds) keeps its name: the cloud's version is fetched beside it (`fetch_to`, the local name differs from the cloud's) and `exec` returns both uploads (`Vec<Work>`: the local file over the cloud's, the older version as a new file). The DB row for the name is written first as "local still as the cloud's" (`Base` from the cloud's `sig_item`), so a failed upload is an ordinary local edit at the next scan, never a second conflict with a second copy of the old file. Otherwise (cloud newer, a tie, or no local sig) the old way: the local file is renamed and the cloud's downloaded. The mtimes are the cloud's own `client_modified` against the local file's: only as right as the clocks of the devices that wrote them. A conflict in a mirror (download only) still sends the local file to the trash.
- **Interrupted upload:** quitting mid-upload leaves a 0-byte item in OneDrive (the API lists it, the web hides it). `run()` turns a `Conflict` of a non-empty local file against a 0-byte cloud file into `Upload` (not in download-only). Without it the real file was renamed `(conflict …)` and the empty one downloaded over its name, again on every restart (nested `(conflict) (conflict)` names). The cause is inferred from the DB and the folder, not seen in a real cloud. **Tried by the owner (Nov 2026) on Dropbox, Google Drive and OneDrive:** quitting FastSync (no Pause first: Pause lets running uploads finish) during a new ~3 GB upload leaves no file in the cloud (the OneDrive web hides a 0-byte item, so only the next `plan` line's `cloud` tells), and quitting during a 320 MB overwrite of a 20 MB synced file leaves the old cloud version at its old size on all three (sessions commit only at the end). So a transfer cut off or failed by "changed while transferring" costs bandwidth, never the cloud copy. Not tried: the restart after it on each provider, and `kill -9`.
- `db.rs`: per-account SQLite (`accounts/<id>/state.db`, `PRAGMA user_version` = 1 since 0.2.0, 2 with the folders table, 3 with `files.r_hash` (`kind:value`, the cloud hash the row's cloud side had, NULL = unknown; written by `Db::set_hashed` where a row comes from a cloud `Item`: transfers, adopt, folder copy/move; `Db::set` writes none and replaces an old hash): a release that changes a table must migrate by it, `CREATE TABLE IF NOT EXISTS` adds no columns): path -> how both sides looked after the last sync, the remote ids, the remote folder ids and the delta cursor. A row is written only after its transfer succeeded.
- **Activity log:** a `log` table in the same `state.db` (`Db::log` best effort, never fails a sync; `trim_log` after every run: 30 days, 2000 rows, `LOG_DAYS`/`LOG_ROWS`). Kinds: `up`, `down`, `trash`, `delcloud`, `conflict`, `move`, `movedir` (kind 9: one row for a folder `move_dirs` renamed whole, path = new folder, msg = old; its files get DB rows but no log rows of their own, and `Report.moved_dirs` makes `run_dirs` skip the cloud rmdir of the old folders), `error`, `stopped` (the guard's counts line), `scan` (values only: path = `full:<cause>` (`rescan` start-up/rescan, `reset` cursor, `feed` a folder change, `now`, `decision`, `rules`, `retry`, `moves` a path run that asked for a full scan, `resume`, `tick`; the first cause of a scan wins, `runner::mark`; shown as the row's caption, an old row with plain `full` has none) or `paths`, size = ms, msg = "changed failed"; worded in the UI so it translates). Written where each action succeeds or fails in `run()`, at the listing/stat errors in `engine.rs`, and by `runner.rs` (a `scan` row when a run moved something or failed, and for every full scan except the quiet 5-minute `tick` of providers without a feed (it would add ~288 rows a day); a path run that moves nothing is not logged, so the 2-minute walk never floods it; tested through a real runner in `tests/runner_scan_cause.rs`; `Warn`/inotify errors). The UI (`crates/app/src/activity.rs`, `LogDialog`) reads it with `db::read_log`, a **read-only** connection of its own (the engine owns the only writer), on a thread; the full list stays in a thread-local and the tabs only filter it. There is no clear button on purpose. Messages stay raw, everything FastSync words (kinds, "5 min ago") is `@tr` in `Tr`; counts are adjectives ("2 changed") so no plural forms are needed. Removing an account or changing its local folder deletes the DB, and the log with it.
- `engine.rs`: `full_scan` (lists both sides; first sync, delta reset, MEGA-style providers) and `sync_paths` (only the paths from inotify or a delta). It talks to the cloud through the `Remote` trait: tests use a plain directory as the "cloud" (no rclone, no network); `rclone.rs` has the real one. The invariants (all tested): local deletes only move to `.fastsync/trash` and only for a file the DB proves we synced; downloads go to `.fastsync/tmp` then rename; a user edit during a download wins; remote names that escape the folder (`..`) are refused; a listing error (a root "not found" included, which once passed as an empty cloud) fails the run and is never read as "everything deleted", and the guard prints its counts to stderr when it trips; a run deleting more than 50% of 10+ known files stops, and so does one that deletes every known file of a folder (at any depth) with 10+ (`Engine::folder_wiped`: an unmounted disk inside the folder stays under 50%; a delete whose local file still exists, i.e. an ignore rule, is not counted; the case-clash code lives in `engine/case.rs`) (a folder of 3 to 9 known files stops only when the run deletes all of them; under 3 is not guarded) (`Report.aborted` = deletes, known, first `engine::SAMPLE` paths; `Status::Stopped` carries the same). **A stop holds the account** until the user answers on the card: the runner saves it as JSON in DB meta `held` (`runner::Held`), runs nothing while it is set (no walk, scan or feed paths, so no "up to date" and no saved cursor; Sync now, rescans and timers are ignored; Pause/Resume re-show the Stopped card and a `Warn` does not replace it), and it survives a restart (the first status is `Stopped`). `Runner::resolve(Decision)` is the only way out: **Delete them** runs a full scan with `Engine.confirmed_deletes = Some(held deletes)`, a cap so a card that sat for days cannot approve a bigger delete than it named (a bigger plan stops again with the new count); **Restore** sets `Engine.restore`, which turns every delete of that scan into the opposite copy (`DeleteLocal` -> `Upload`, `DeleteRemote` with no local file -> `Download`, with one -> `Forget`; never in download-only, whose card offers only Delete). `held` is cleared only after that run finished without errors (after errors the decision stays and the retry carries it out). A stop is shown on the card (the paths go in `AccountRow.detail`; the "…and N more" line in `main.slint` hard-codes `SAMPLE` = 5), as `Overall::Stopped` in the tray, and once as a desktop notification (`notify.rs`, zbus `Notifications.Notify` on a thread; `State.warned` holds the accounts already announced, an `Idle` status clears it; the Flatpak needs `--talk-name=org.freedesktop.Notifications`).
- **Trash size / Empty (Settings):** `engine::trash_dir|trash_usage|empty_trash` (never follow symlinks). `trash_job` in `main.rs` counts (or empties, then counts) every account's trash on a thread; `TRASH_GEN` drops a stale answer, and `on_scan_trash` skips while `trash-busy`, because Settings re-creates itself (and calls it from `init`) right after the `EmptyTrashDialog` (opened from Settings like About, both buttons return there). A removed account's trash is no longer counted (its folder is no longer known): the removal thread runs `purge_trash` once with the current limit and leaves the rest (the Remove dialog says so). It must not delete `.fastsync/tmp` or the folder: the same folder may already belong to a new account that is writing there.
- **Trash age:** `settings.trash_days` (default 90, 0 = never, clamped to `MAX_TRASH_DAYS`). `engine::purge_trash` deletes `trash/<unix seconds>/` batches whose folder name (the time it was trashed, not the file's mtime) is old enough; non-numeric folders stay. A thread started in `main.rs` runs `purge_all` at start-up and every 6 h and reads the limit from the `TRASH_DAYS` atomic, never from the UI thread's `Settings`; changing the SpinBox saves it and runs one pass at once. Not started in fixture runs.
- **Built-in ignored names:** `engine::ignored` (case-insensitive for the native/OS names: `.dropbox*`, `.tmp.drive*`, `.debris`, `.DS_Store`, `Thumbs.db`, `Desktop.ini`, `~$*`; also `.fastsync`, `.part`, `.swp`...) is checked on the local walk, the cloud listing (`safe_rel`) and inotify (`runner::rel`), so such a name is invisible on both sides. Not a user rule on purpose.
- **Moving files into place (`engine.rs`):** `trash_move` (trash) and `rename_over` (downloads) fall back to copy + rename when the rename fails with `CrossesDevices` (a disk mounted inside the synced folder; `.fastsync/tmp` is on the root's file system). `rename_over` copies to `<name>.fastsync.part` beside the destination (`ignored` hides `.part`, so a kill between the copy and the rename leaves that file for good: accepted, the window is tiny); `copy_with_time` keeps the mtime the sync compares. **An overwriting download** (`fetch_to`, `expect_local` is Some) first renames the old file into `.fastsync/trash/set-aside/*.old` (not `tmp`: start-up empties `tmp`; `purge_trash` keeps non-numeric folders, so only Empty Trash clears a leftover there) and looks at it: unedited = installed with `hard_link` (fails if the name was taken) and the old one dropped, or put back if the install failed; edited in the window = put back, or trashed if the name is taken again, and the run retries (`CHANGED`). The delete guard's report is `report_stop`.
- **Ignore rules:** `ignore.rs` (`Rules::parse|matches`, own small gitignore matcher; no `ignore`/`globset` crate, they pull `regex`) reads `<root>/rules.fastsyncignore` (`RULES`, never ignored itself, synced like any file). `Engine.ignore` is consulted first in `run()`: a synced file (DB row + cloud copy) that now matches gets `DeleteRemote` (the Dropbox way: cloud copy goes, local stays, counted by the delete guard), a row without a cloud copy or in download-only gets `Forget`, anything else is skipped; `skippable` keeps ignored never-synced paths out of `sync_paths`/`local_changes`. `scan(root, skip, ignore)` does not enter a folder `Rules::matches_dir` hides (nor does `sync_paths` for a folder event inside one), so a path missing from its result must be read as "ignored", never "deleted": `run` applies the rules before anything else, and `local_changes` filters the DB rows with `ignore.matches` for the same reason (without it every walk would call them deleted). `runner.rs` re-reads the file every loop turn and folds its text into `excluded_key` (picker, `\n\0\n`, rules). **A change is looked at by path when it can be** (`Rules::change`: only hiding rules added or removed anywhere in the same order = `HidesMore`; only anchored literal hiding rules removed = `Unhides(names)`; anything else, a wildcard or unanchored name removed, a `!` added or removed, a reorder (the last rule wins, so the same lines can show a hidden file), a mix, = `None`), for a provider with a feed: `rules_delta` queues the synced files the new rules hide (DB rows; the run makes `DeleteRemote`, counted by the guard) and the un-hidden names (paths + folders to list) in `feed_paths`/`feed_dirs`, and `walk` finds local files they used to hide; the `excluded` key is then confirmed by that run (`rules_run`; a held account drops the queue and marks a full scan instead). At start-up the same happens when only the rules part of the saved key differs and there is a saved cursor (`rules_since_last_scan`). `None`, a picker change, a first sync, or a provider without a feed (MEGA) is a full scan as before. Change `ignore.rs` only with a test. **An unreadable rules file is never "no rules"** (`runner::read_rules`: only "not found" is empty; UTF-16 from a Windows editor, no permission): at start-up the worker ends with the error (only a restart or saving the account starts it again), later the runner keeps the old rules, logs the error once and runs nothing until the file reads again (`rules_bad`), because empty rules would upload every file they hide.
- **Download only:** `Account.download_only` -> `Engine.download_only` makes `run()` use `decide::decide_down` (never `Upload`/`DeleteRemote`; `exec` refuses them too). A local edit or local-only file goes to the trash, the cloud copy wins. The delete guard's `known` is then max(DB rows, local files in the run), because a new account has no rows. The flag travels Add/Edit dialog -> `Picker.download_only` -> `apply_folders`, which restarts the runner when it changes.
- **Looking up changed paths (`engine::lookup`, used by `sync_paths`):** one `stat` per file cost 30-60+ s for 84 new files (before any transfer started). The paths are grouped by parent folder; a folder with more changed files than its listing has pages (`Db::count_in` / 1000 + 1) gets one non-recursive `Remote::list_dir` (`operations/list`, paths from the fs root, checked through real rclone), the rest is `stat`; all of it `PARALLEL` at a time. **Gone folders answer for everything below them:** `lookup` runs in two rounds (a job with another job's path above it waits), and what round 1 proves gone (a `Dir` job that passed `folder_gone`, or a `stat` that said none) answers for the second round without a call; in `sync_paths_in` a path under a folder listed whole or confirmed gone (`listed_roots`) that the listing does not show is "not in the cloud" with no `stat` (a rename by case alone is excluded: it needs the real answers). **A rename the watcher saw** (`EventKind::Modify(Name(Both))` -> `Event::Moved(from, to)` -> `Engine.local_moves` for that one run, cleared after; also a full scan uses it): a moved folder (rows under `from`, a local folder at `to`) is added to `dirs`, so both names are listed once and answer for everything below; `pair_moves` pairs an upload with a delete without any hash when `renamed_here(old, new)` and the new file's `Sig` equals the old row's `Base.local` (an edited file hashes as before; the cloud side is still proven by `cloud_unchanged`/`dir_move_proven`), which also makes single-file renames work on MEGA. **The Dropbox feed's echo is dropped** (`Engine::feed_echo`, applied to the batch in `runner.rs` before `delta::impact`; `Change.size/mtime` are only filled by Dropbox): a deleted entry with no row at or under it in any case (`Db::knows_ci`) and nothing on disk, or a file entry equal to the row's cloud `Sig` with the local file still as synced; folders and anything unsure go through. The cursor moves as always. Not done: a cloud-side rename split over two feed batches of fewer than 50 deletes still costs a trash and a download; Drive/OneDrive have `Engine::feed_echo_id` (the change carries id, size, time and hashes: Drive `size,modifiedTime,md5Checksum` in the `changes.list` fields, OneDrive `size`, `file.hashes`, `fileSystemInfo`): a file entry is dropped only when the row of that id (`Db::by_id`) has the same name in the same folder (the folder map resolves the parent), the same size, a hash of the same kind equal to `r_hash`, the same time when given and the local file still as synced; a row without a hash, or any doubt, goes through (a lookup, as before). Untried against the real feeds: that the feed's time equals what rclone lists (OneDrive: `fileSystemInfo`) and that the hash kinds match (`md5`; `sha1`/`quickxor`); both degrade to "not an echo". A listing error falls back to `stat` per file. A "not found" listing counts as "the folder is gone" (every path `None`) **only** when `stat` of the folder itself also says gone (one extra request; it is what keeps 84 deleted files from costing 84 `stat`s), never for the root; anything else falls back to `stat` per file, so a listing glitch is never read as a cloud delete. The trait default for `list_dir` is an error, so a test remote without it just uses `stat`. A listing matches names exactly, `stat` on Drive/OneDrive is case-insensitive: not tried against a real account. **Names that differ only by case (`Engine::settle_case_clashes`, rules in `decide::resolve_case_group`, tested on facts alone), in `full_scan` and in `sync_paths_in` (`case_siblings`: one `read_dir` per folder finds namesakes the watcher did not mention):** Dropbox and OneDrive take them for one file, so, as Dropbox's own client does (checked by the owner): (1) **a rename by case alone** (`MyFile.txt` -> `myfile.txt`: the old name has a DB row and no local file, the new one is a new local file) is a rename, never a clash: both names go through the plan, the new one is read as having no cloud copy (`Settled.renames`; a case-insensitive cloud answers for it with the old file, which used to be adopted while the old name became a cloud delete of the only copy), `pair_moves` pairs them and `MoveRemote` does `Remote::rename` (`movefile`). **The new name only counts as "no cloud copy of its own" when the cloud's answer for it is the old file** (`is_old_file`: same `id`, else another spelling, else same size and time): a cloud that allows both names (Drive) may already hold another device's file under the new one, and moving onto it would overwrite it (that is then an ordinary conflict). `case_siblings` also asks the DB (`Db::paths_ci`, one lookup per changed path through the expression index `files_lpath` on `lower(path)`, added with `CREATE INDEX IF NOT EXISTS`: no table changed, so no `user_version` bump; SQLite's `lower` is ASCII-only, so a non-ASCII-only case difference is found only from the disk listing or when the old name is also reported), so a watcher run that reports only the new name still finds the old one and looks at both. `MoveRemote` skips its "appeared in the cloud" check only for that same file, and **never falls back to upload + delete** (on a case-insensitive cloud the upload lands on the old file and the delete removes the only copy): when the direct `rename` fails it goes **through a temporary name** (`rename_by_case`: `to` + `CASE_TMP`, two renames, a failed second one is undone), and only if that fails too is it an error, retried. **A folder renamed by case alone** (`Docs` -> `docs`) cannot be done file by file (the cloud answers for `docs/a.txt` with the file in `Docs`): `move_dirs` treats a case-only group as a folder move even for one file, checks the temporary name is free and does `move_dir_by_case` (two `move_dir`s). **Every case-only rename is checked, whatever it answered** (`spelling_kept`: the cloud's own non-recursive `list_dir` of the parent must show exactly the new spelling, `stat` may echo the asked-for one; a remote without `list_dir` is accepted unchecked): a direct rename that said "ok" and changed nothing goes on through the temporary name, and one that still does not show the new spelling is an error with no DB row written (a row would make the pair a name clash at every later full scan). A case-only move of a file whose **folder part** differs (the folder was renamed but `move_dirs` could not move it whole, e.g. an unknown file in the cloud folder) is a clear error, never a per-file move. A crash between the two steps leaves a `….fastsync-case-tmp` name in the cloud (a folder of it is downloaded and the local one uploaded again at the next scan: slow, nothing lost). Unverified on Dropbox/OneDrive: whether even the two-step rename changes the stored spelling; (2) **a second, new file** is renamed locally to `myfile (Case Conflict).txt` (`decide::case_conflict_name`, `Engine::plan_case_conflict` picks the name, `case_renames` holds the plan, `apply_case_renames` renames **inside `run`, after the delete guard and the cancel checks** (a stopped run leaves the user's files alone; one that changed meanwhile stays and its upload is dropped); regular files only, never over an existing or planned name, logged as kind `conflict` and added to `Report.conflicts`, so the user is told) and goes up as a file of its own; the oldest keeps its name when none was synced; (3) two names that were **both** synced before, a mirror (never renamed), or a file that cannot be renamed are `Report::skip`ped as before. `lookup` answers `CLASH_WHY` for a path whose cloud folder listing holds only another spelling, or whose `stat` returns an item with another spelling; `sync_paths_in` then makes the Case Conflict rename. **Not done:** the same by case alone in the **cloud** (cloud `MyFile.txt` -> `myfile.txt`): `full_scan` leaves the two names alone as a clash, a path run may download a second local copy. **Unverified:** that rclone's `movefile` renames by case alone on Dropbox/OneDrive (rclone has special handling for case-insensitive remotes, not tried: until verified the rename may show the error above, nothing is lost), and whether rclone's `operations/stat` returns the stored spelling or the requested one on Dropbox/Drive/OneDrive; if it echoes the request, a lone new `report.txt` beside a cloud-only `Report.txt` is not caught by the `stat` path (only by the listing path, or the next full scan).
- **Audit fixes (Nov 2026), non-obvious parts:** (1) the rules file travels like any file, so in `run` a plan that uploads `RULES` while a rule deletes cloud copies uploads it first (after the guard, `run_transfers` on just that job; a failed upload holds the rule-caused deletes), and a plan that *downloads* `RULES` holds every `DeleteLocal` (`fail`, retried; the next run has the new rules and makes them `Forget`): otherwise another machine read the deletes as ordinary ones and trashed its files. (2) An overwriting download sets the old file aside in `.fastsync/trash/set-aside/`, never `tmp`. The held deletes of (1) go to `Report.later` (no card). (3) `Engine.case_blind` (Dropbox/OneDrive only, set in `runner::work`; `Engine::new` defaults to true) gates `settle_case_clashes` and `lookup`'s `CLASH_WHY`: Drive and MEGA keep `A.txt` and `a.txt` as two files. (4) `runner::respell_dropbox` puts the folder part of Dropbox feed paths into the spelling the DB knows (`Db::dirs_ci`, index `folders_lpath`, only when exactly one case-blind match); the last part stays as reported. (5) A new unknown file or folder of Drive/OneDrive whose name rclone re-encodes (`delta::rclone_encodes`) forces a full scan: the feed's raw name builds a path that finds nothing. (6) `OneDrive` runs with `Personal Vault` in `Engine.excluded` (the feed's `list_under` has no rclone filter). (7) The watcher does not follow symlinks. (8) The feed's root-id loop warns from the 3rd failure with a doubling wait, like the poll. (9) `Adopt` rows are written `ADOPT_BATCH` (1000) per transaction (`Db::begin|commit`). (10) `scan_from` walks a folder a watcher event reported with its root-relative prefix, so rules and unchecked folders cut whole folders. (11) `pair_moves` indexes old paths by (size, name) and (size, folder). (12) `runner::removes_synced` (a watcher path that is a synced file or folder gone from the disk) sets `hold_until` to `LOCAL_DELETE_HOLD` (10 s) on top of the 3 s burst wait, so remove + write again is one run; the README says deletes and renames reach the cloud ~10 s later. (13) `Db::commit` rolls back and returns the error on failure (`Engine::commit_rows` reports it as a "state database" error); the adopted rows of that batch are adopted again by the next scan. (14) `trash::recover_set_aside` runs at runner start: leftovers of `trash/set-aside` go to `trash/<now>/recovered/` (original path unknown) with a log row. (15) `move_dirs`' case-only branch also needs `case_blind`. (16) `open::xdg_open` ignores a target starting with `-`.
- **Which paths a run looks at (`Engine::paths_to_sync`):** inotify paths pass `filter_local` (a path whose local file equals its DB row is the echo of our own write); paths from the cloud's feed never do (a cloud edit or delete leaves the local copy untouched, so the filter dropped it and the cursor then moved past the change). `runner.rs` keeps the two in `pending` and `feed_paths`. **Also in `run`/`full_scan`:** two cloud files with one name (Drive) are skipped with an error, like a case clash; an upload of a path the plan saw no cloud file for first `stat`s it and refuses if one appeared; `Engine::trash` never replaces an earlier trashed copy of the same path (`.1`, `.2` suffix); the folder check rejects `..` and judges symlinks by their target.
- **Parallel transfers:** `run()` does deletes, conflicts and DB-only actions one at a time first, then `run_transfers` runs the uploads and downloads `PARALLEL` (4) at a time on scoped threads. Workers call the free fn `transfer` (no DB, so `Remote` is `Send + Sync`); every DB write, log row and counter stays on the run's thread (one SQLite connection). `Progress` shows the file that started last, `done` counts finished ones. Download temp names carry a counter. A cloud's 429s are rclone's to retry; lower `PARALLEL` if a provider complains. `Rclone::list` deserializes straight into `Entry` (a listing that does not parse is an error, never a shorter list).
- **First scan of a big cloud (100k+ files on Dropbox sat 11+ min on "Checking for changes…", measured: rclone idle on one open connection, 0 DB rows, so the time is the one recursive `operations/list`):** `RcloneRemote::list_progress` (`Remote::list_progress`, default = `list`) is `walk_cloud` (a free fn over a `list_one` closure, unit-tested with a fake cloud) and works a queue of folders `PARALLEL` at a time: the top `SPLIT_DEPTH` (3) levels one level per call (their subfolders join the queue, so the total grows), deeper folders as one recursive call each (splitting only the top level left the two biggest folders as two long calls stuck at "24 of 26"); it reports folders done/found; any failed part fails the whole listing, and two same-named sibling folders (Drive) fall back to the single `list()`. `Progress.phase` (`Phase::ListCloud|ScanLocal|Compare`, default `Transfer`) is set by `full_scan` and `run` (also the Adopt-only stretch of the exec loop); `runner::ticker` sends non-transfer phases too and fills `Progress.secs` (the clock; no rclone call). `main.rs::live` maps them to `AccountRow.transfer` 4/5/6 with the clock in `speed`. `Engine::adopt_identical` runs the equal-size `same_content` hash checks (each reads a whole local file) `PARALLEL` at a time after the planning loop. **Not measured on the real Dropbox:** whether the split listing is faster than one call (Dropbox may throttle; one huge top-level folder gains nothing) and where the 11 min went; the listing has no percentage, only folders done and the clock.
- **A failed or paused listing resumes (`rclone::Listed`, in `RcloneRemote`):** `list_progress` keeps every folder it listed whole, and a walk that fails or is cancelled leaves them for the next try; a walk that completes clears them. The feed cursor is taken before the first scan and keeps polling during it, so what the cache may have missed arrives as events: `runner.rs` calls `Remote::forget_listed` for each `Event::Remote` (Dropbox: the reported paths, which drops those folders and their parents and children; Drive/OneDrive report ids, so everything), `Event::Reset` and Sync now (everything), and after every run of some paths, for the paths it looked at (`run_changes_cloud`: dropping everything each time would leave a busy machine nothing to resume; our own upload's feed echo can arrive after the next scan, and a kept folder without the new file would read as a cloud delete of a file we synced). The match is case-blind (Dropbox's feed spells folders differently than the listing), and only a folder whose listing took 2 s or more is kept (`KEEP_IF_SLOWER`: a copy of every folder would double the listing's memory). `max_age` is 60 min, 10 min for a provider with no feed (MEGA). Also each folder's listing is retried 3 times when the error looks transient (`retry_transient`: 20/40/60 s; a 401 or "not found" fails at once) and a failed full scan is not retried sooner than it ran, at most `COOL_DOWN_MAX` = 5 min (`Retry::cool_down`; the kept folders make the retry short). Not tried against a real Dropbox; the known race (a change during an attempt is applied only after it) is the one a single long listing already had.
- **Pause/Stop end a run in progress:** the worker reads its events only between runs, so `Runner::pause(true)` and `stop()` also set `Engine.cancel` (shared `Arc<AtomicBool>`) at once. `run()` checks it before the guard (a cut-short plan is never judged), before each one-at-a-time action, and `run_transfers`/`adopt_identical` workers before each job: transfers under way finish, none starts; `Report.cancelled` is set and the runner `continue`s without saving a cursor, the `excluded` key, a `held` decision or an "up to date" status; a cut-off full scan sets `full` so resuming scans everything, a cut-off run of some paths puts those paths back in `feed_paths` (`ran`) instead, so resuming costs no listing. An idle Pause (no run cut short) does not: `Pause(false)` only sets `walk`, and the feed/inotify paths queued meanwhile are synced (`pending`/`feed_paths` survive the paused `continue`), so a resume costs no cloud listing. Only the worker's `Event::Pause(false)` clears the flag (never before a run, or a Pause pressed as a run starts would be lost). The cloud lookup of `sync_paths` (`lookup`) and the move/copy pairing loops check it too. **`runner::EndRun`** (drop guard) raises the ticker's `over` flag even when the run panics: `thread::scope` joins the ticker before it lets a panic out, so without it a panic (now catchable, no `panic = "abort"`) hung the worker for good. `runner::clean(&Report)` (no errors but skips, no guard stop, not cancelled) is the test for "may this run confirm the `excluded` key or a held decision"; the feed cursor has the looser `Retry::may_confirm` (see the retry paragraph). Timers (`timer`) sleep one whole interval, no per-second wake-ups, and end at the first tick after the worker is gone. A listing stops between folders (`Remote::list_progress(.., cancelled)` fails with "cancelled", never a partial list; `full_scan` then returns `cancelled`, not an error, and also checks after the local walk and every 256 paths of the plan); the rclone call under way finishes. `panic = "abort"` is **not** set in the release profile: it would make the runner's `catch_unwind` (one account's panic = an error card, not a dead app) do nothing.
- **Symlinks:** `scan` never lists a link, and nothing is read or written under a symlinked folder (`under_symlink`, `refuse`); `run()` plans nothing for a path with no listed local file where `symlink_metadata` finds something (a link holds the name), or the download failed on every retry, no run was ever clean and the feed cursor was never saved (a full scan at every start). The official Dropbox client syncs a link as an **empty file whose target is only in the file's metadata** (`symlink_info.target`; rclone does not pass it on, `Rclone::list` hashes show the empty-content hash). `make_link` (in the transfer workers, before `transfer`) handles a planned `Download` of a new 0-byte file with no local file and no `from`: `Remote::link_target` (`RcloneRemote`: Dropbox only, one `files/get_metadata` through `delta::dropbox_link_target` with rclone's token) and, if it is a link whose target passes `safe_link_target` (relative, ≤4096 bytes, never above the root by names alone), `symlink()` (fails if the name exists). **No DB row** (`Done::Link`): `local_sig` cannot describe a link, and a row would read as "deleted here" later; the next scan is stable only through the planning check above. An unsafe target is `Done::Skipped` (no error, not logged, retried at each scan); a failed lookup is an error (retried), so a glitch never makes an empty file. Local links are never uploaded (the API has no way to create one: the `symlink_info` field is in `FileMetadata` responses only). Costs one metadata request per new empty Dropbox file (every `__init__.py` of a first sync). Not tried against the real Dropbox end to end (only the field's shape, read through the API); a link deleted here comes back at the next scan; a cloud delete of the entry leaves the local link; team-space accounts may need a path-root header; a relative target through another link can still leave the folder (only names are checked).
- **Providers without a feed (MEGA):** the 5-minute timer sends `Event::Tick`, not `Full`; `scan_due` drops a tick when the last full scan ended less than `SCAN_EVERY / 2` ago, because ticks pile up behind a long run and a listing slower than the interval would otherwise restart the moment it ended. `scan(root, skip)` does not enter unchecked folders. A **new** download is linked into place with `hard_link` (fails if the name exists; falls back to `rename` where hard links fail), so a file saved since the check is never replaced; an overwrite of a file we synced still uses `rename`. `Rclone::speed` has a 5 s limit (`send_within`), the only timed call: the ticker runs inside the run's thread scope. `trash.rs` holds the trash functions (re-exported from `engine`). `main.rs::clashes` compares the accounts' folders by their real paths too (a symlink to another account's folder).
- **The account cards' model is long-lived:** `main.rs::refresh` keeps one `Rc<VecModel<AccountRow>>` (`ROWS`) and `sync_rows` changes only the rows that differ, because a running sync reports once a second and a new model each time recreated every card (a click or a text selection spanning that moment was lost). Fixtures set their own model and do not exercise this path. `emblem::set` runs `gio` on a thread of its own (it is called from the sync worker, and `gio` can wait long on the metadata service).
- `delta.rs`: `RemoteChanges` per provider (Dropbox cursor + long poll, Drive `changes.list`, OneDrive `/delta`) with JSON parsing split from HTTP so it is tested on canned answers. Drive/OneDrive report ids, so `impact()` turns them into paths with the folder ids the DB keeps; a folder **moved, renamed or deleted** there (a known id) is looked at by path, like Dropbox's: `Impact.dir_moves`/`dir_gone`; the old path (the engine finds the files under it in its rows) and the new one (`Impact.dirs`: listed whole, so `pair_moves`/`move_dirs` pair the files into moves) go to the run, and the runner's folder map follows with the cursor (`runner::DirOp` Add/Move/Drop, applied in order to the in-memory map for the next batch and to the DB by `save_dir_ops`; `Db::move_dir_ids|drop_dir_ids`). Still a full scan when the new parent is unknown, when two folder changes of one batch touch each other (or a folder is made inside one that moves: the paths would come from a map the batch makes stale), or when the new name is one rclone re-encodes (`respelled`). Our own folder rename's echo is one listing, not a scan. A batch of 50+ removals is held for one poll (`mass_delete`) for every provider. **A folder created there is not one** (`Impact.new_dirs`): `impact` resolves its path from its parent's (the saved `dirs` map, the runner's `dir_adds` of earlier unsaved batches, or a folder of the same batch, repeated until nothing more resolves), lists it alone through `Impact.dirs` like Dropbox's, and the runner saves the new `(id, path)` rows with the cursor that moves past them (`Retry::persist_with`: failed paths, then `Db::add_dirs` (`INSERT OR IGNORE`), then the cursor, so a replayed batch finds the folder known only after its listing ran; a full scan clears `dir_adds` because `set_dirs` replaced the table). Every folder FastSync uploads comes back this way: it used to be a full scan each time. A folder that moved in from an id we never saw, or a deletion whose parent is known, is still a scan. Untried against real Drive/OneDrive. **Dropbox reports paths:** a new or moved folder entry (also the echo of a folder FastSync itself uploaded into) goes into `Impact.dirs`, which the runner keeps in `feed_dirs` and hands to `Engine::sync_paths_in(paths, dirs)`: one recursive `Remote::list_under` per top folder (`feed_dirs_to_list` drops reported subfolders; `list_folders` lists `PARALLEL` at a time; more than `FEED_DIRS_MAX` = 30 are first climbed to their parents (`feed_dirs_to_list`: the deepest level replaced by its parent, repeated; a parent is a recursive `list_under`, never more than the full scan reads, but with no progress or cancel inside the call); only a set that is still longer at the top level sets `Report.wants_full` and the runner runs a full scan instead, nothing touched) (after `forget_cache`; its items answer for their paths, so no `stat`), not a listing of the whole cloud (10+ min on 100k files). A folder that cannot be listed is a failure of its own (`Report::failed_dirs`, `Report::fail_dir`; kept in `Retry.dirs` and listed again alone, never a full scan, and the cursor may move on); "not found" for it is "gone" only when `engine::folder_gone` agrees (also used by `lookup`: not the root, and the folder's own `stat` says gone). A batch of `SPLIT_MOVE_MIN` (50) deletions is `Impact.mass_delete`: the runner holds the run for `MASS_DELETE_HOLD` (60 s, `hold_over`) so the new name of a folder renamed in the cloud (the next batch, or any batch) joins it and `pair_moves`/`move_dirs` pair them; a stop in the path run still escalates to a full scan (a smaller split move costs a trash and a re-download). **A listing that failed (`Report::failed_dirs`) holds every `DeleteLocal` of that run** (`run`, after the pairing: a renamed folder whose new name could not be listed would read as deleted, and the guard cannot judge a small share of a big account): they are `fail`ed, so retried with the folder. Expired cursors (`Poll::Reset`) trigger a full scan and a new cursor.
- `runner.rs`: one worker thread per account owns the engine and DB, fed through one channel by the inotify watcher (debounced), the delta poller and timers (a local walk: the event ticks every minute (`WALK_TICK`) and `walk_due` decides, from the Preferences settings `walk_minutes` (default 5, with a working inotify watcher) or `walk_fallback_minutes` (default 2, when the watcher failed to start or `WATCH_LIMIT_HIT` is set), both 1 to `MAX_WALK_MINUTES` (60) and read from the `WALK_MINUTES`/`WALK_FALLBACK_MINUTES` atomics so a change applies at once; a full scan every 5 min without a feed; a retry after errors, waiting 1, 2, 4, 8, 16, then 30 minutes while runs keep failing: `retry_after`). **A failed file is retried by itself, not by a full scan (`Retry`; a listing of a big cloud took 10+ min on a 100k-file Dropbox, during which nothing else syncs):** `Report` tells the errors apart: `fail(path, why)` (one action on one path failed: `log_failed`, `adopt_identical`'s "could not compare", a `sync_paths` lookup; a move's old path too) goes to `Report.failed`, `skip` (a name clash or two cloud files with one name: state, only `full_scan` checks them, so a path retry would bypass the check and must never run them) is shown and never retried, and whatever is pushed straight into `errors` is global (`has_global_failure`: the cloud listing, the state DB, `drop_excluded`) and needs a full scan. `Retry` keeps `paths` (`failed` + `later`) and `dirs` (`failed_dirs`), together at most `RETRY_PATHS_MAX` = 5000, then a full scan, `full`, the `retry_after` back-off, and writes `[full, paths]` (`[full, paths, dirs]` when a folder failed; both load) as JSON to DB meta `retry` (`Retry::save`, only when it changed) **before** the feed cursor is saved, so a restart retries just those paths (`Retry::load`: due at once; an unreadable value means a full scan). `take_due` gives `Due::Paths` (they join `feed_paths`, never `filter_local`) or `Due::Full`; `record(report, ran, did_full)` removes the paths a run looked at, adds its failures, and a clean full scan replaces everything. **`Retry::persist` does both writes in the one order that is safe (the failed paths, then the cursor, and the cursor only if the first worked and `may_confirm`; tested with a DB that refuses the `retry` key). The cursor (`Retry::may_confirm`) is saved unless the run was stopped, cancelled, had a global failure, or a full retry is waiting:** path failures no longer hold it, which is what made every restart scan the whole cloud. `clean(&Report)` (no errors except `skip`s, which are states: a permanent clash must not keep anything from being confirmed; no stop; not cancelled) stays strict for the `excluded` key and a held decision, and a held decision is only cleared by a clean **full** scan (`Retry::escalate` (through `Retry::finish_run`) makes the retry a full one while a decision is pending, since a failed path does not carry it out). The unchecked-folders/rules key uses the looser `runner::settled` (a whole scan, no stop, not cut short, no global failure; failures of single files do not hold it, they are retried by path, and a folder that could not be trashed is a global error), or one stuck file cost a listing at every restart. `after_cancel` says what a cut-short run leaves (a full scan starts over, a run of paths re-queues its paths and `feed_dirs`). The cursor is also held back when `Retry::save` could not write the `retry` value. **A file that changed under its transfer is not an error:** `transfer` turns an upload failure (rclone's "corrupted on transfer" hash check on a file saved meanwhile) into `CHANGED` when `local_sig` differs from the plan, and `fetch` does the same for a download; `run_transfers` puts the path in `Report.later` (no log row, no red card, retried in 60 s, then 2, 4 ... 30 min while it keeps changing (`later_fails`, apart from real failures: a database or VM image that never stops would otherwise be uploaded in part every minute; inotify events for it still start a run each, a per-path cooldown for that is not done), and the edit's own inotify event normally syncs it first). The feed poll's `Warn` goes out only from the third failure in a row (a 429 or a blip is no Problem row); its wait is 30 s doubling to 10 min and never shorter than the service asked (`Retry-After` header, copied into the body by `delta::finish`, or Dropbox's `error.retry_after`; `fail` writes `(retry after N s)`, `delta::retry_hint` reads it back; an HTTP-date value gives no hint). The feed's recovery after a failed poll sends `Event::Recovered` (a walk to clear the old message), not `Event::Full`: its cursor did not move, nothing was missed. The retry timer's wake-up is `Event::Retry` (it used to be `Full`). Still a full scan: first sync, no cursor, a cursor `Reset`, a changed unchecked-folders list or rules file, a held decision, Sync now, a global failure. Unit-tested (`Retry` is pure); not tried against the real Dropbox. A panic in the worker is caught in `spawn` and shown as an error status. Pause, Sync now, Resolve (the answer to a stopped run), Stop are events. When inotify runs out of watches (at start-up, or later through the watcher callback's `MaxFilesWatch` error) the runner sets `runner::WATCH_LIMIT_HIT`; `on_scan_trash` (every opening of Settings) turns it into `watch-fix`, the sysctl command Preferences shows (`watch_fix_command`). Only a restart clears it. The 2-minute walk only shows "Syncing" when it finds paths. **Conflict alert:** `Report.conflicts` (paths) is collected by the runner; every run that leaves any pending pushes `alert_at` to now + `CONFLICT_QUIET` (10 s), and the top of the loop calls the second `spawn` callback `on_conflicts(count, first path)` once it is due (not part of `Status`, so no card/tray change; `main.rs` words it from `Tr` and sends it critical through `notify.rs`). A restart drops unannounced ones (they stay in the log). **Notification clicks:** `notify::send(summary, body, actions, on_action)` always declares a `default` action and keeps the handler by the id `Notify` returned (`HANDLERS`, dropped on `NotificationClosed`); `listen` subscribes to `ActionInvoked`/`NotificationClosed` once, before the first `Notify`, on the kept `BUS` connection. A click on the conflict alert raises the window and opens the log on Problems; one conflict adds a `show` button (`show_file` in `main.rs`: `FileManager1.ShowItems` with `file_uri`, else `xdg-open` of the folder, which is also what the Flatpak gets); the stop alert's click only raises the window. A log row that leaves a file on disk (`LogRow.path`: up, down, conflict, move) has the same folder button (`log-show-file`). Unverified in a live desktop: that Cinnamon's notification server reports a click on the body (`default`) and on the button, and that Nemo selects the file. The timer path is untested (needs a real conflict through `spawn`); only `Report.conflicts` has a unit test.
- Embedded OAuth client: `rclone.rs::embedded_client` bakes the project's own Google/Dropbox/OneDrive client ID at build time (`option_env!` of `FASTSYNC_{GOOGLE,DROPBOX,ONEDRIVE}_CLIENT_{ID,SECRET}`, from the repo secrets `{GOOGLE,DROPBOX,ONEDRIVE}_CLIENT_{ID,SECRET}`, mapped in `appimage.yml` and `flatpak.yml`; `flatpak/build.sh` hands them to the sandbox through the gitignored `flatpak/embedded.env`). The user's own ID wins; unset (local builds, forks) means rclone's shared ID. The secret is readable in the binary.
- **rclone is restarted when it dies:** `Rclone::send_within` retries a failed call once after `revive`, which starts `rclone rcd` again on the same port and password (so every runner's `Arc<Rclone>` keeps working); `restarts` tells "restarted since" from "same process, other failure", `closed` (set by `shutdown`) keeps a quit from bringing it back. `engine/pair.rs` holds `pair_moves`, `pair_copies` and `adopt_identical` (their tests stay in `engine.rs`, with the fixtures). The emblem `gio` calls go through one ordered queue thread.
- Tokens: delta clients read the access token from rclone's config (`Rclone::token` first makes rclone refresh it when close to expiry).
- The synced tree is always the cloud's **root**: there is no `remote_path` (selective sync replaced it).
- **Rename/move detection (`Engine::pair_moves`, called in `run()` before the delete guard counts, so a rename is never a delete):** a `DeleteLocal` (DB row, local copy untouched) is paired with a `Download` of the same size, and a `DeleteRemote` (cloud copy, no local file) with an `Upload`, when `Remote::same_content` proves equal bytes (the listing's hash against `Rclone::local_hash`). **No hash (MEGA):** the pair also counts when the file **name is kept** and the new side's size and mtime are exactly the old row's (`Base.local` for an upload, `Base.remote` for a download), the only proof there is (a different file with the same name, size and mtime would be wrongly moved; the name is required because archives and `rsync -t` give whole batches one size and time; providers with a hash never use this). So on MEGA a folder rename or a move to another folder pairs, a rename of one file does not. Candidates must share the file name or the parent folder, same-name first, `PAIR_TRIES` hashes per new path (sequential, on the run's thread). The pair becomes `Action::MoveLocal` (`fs::rename`, checks the old file is unchanged and the target absent) or `MoveRemote` (`Remote::rename` = `operations/movefile`; checks the cloud copy and that the target is free; if the move fails it uploads and deletes the old, as the unpaired plan would), run in `run_transfers` with the new `Work.from` (`Moved`: the old path). The new DB row is written first, then the old one forgotten. Never `MoveRemote` in download-only (`refuse`). Log kind `move` (path = new, msg = old path; kind 8 in `activity.rs`, `is_file`). Tested with `DirRemote` and through real rclone (`rclone_local.rs`); `movefile` is not tried against Dropbox/Drive/OneDrive. A rename split over two runs (two inotify bursts) falls back to upload + delete. **Folder move (`Engine::move_dirs`, just before `run_transfers`):** the `MoveRemote` jobs are grouped by the folders left once the common ending of old and new path is cut off (`dir_pair`: `a/x/f` -> `b/x/f` is `a` -> `b`); a group of 2+ files becomes one `Remote::move_dir` (`sync/move` of folder onto folder, `Rclone::movedir`, which rclone does with the service's own `DirMove` where there is one) only when `dir_move_proven`: neither folder excluded, `Db::under(old)` has exactly the group's files (no other synced file moves along), the unfiltered `Remote::list_under(old)` holds exactly those files with the synced sizes/times (nothing another device added, nothing ignored or hidden), `stat(new)` is `None` (a move onto an existing folder merges), and the new local files are as planned. Then `forget_cache`, `list_under(new)` and a row per file (size must match; with a good listing a file it does not show stays a one-by-one job, which fails its own `cloud_unchanged` and is sorted out next run; with a failed listing every file gets its row from what the old row knew, since a move keeps size and time). Any failed proof or call leaves the per-file moves. Tested through `DirRemote` (`Counting`) and real rclone's `local` backend (folder inode kept); **not tried against Dropbox/Drive/OneDrive**: whether their `DirMove` is used through `rcd`, and whether a failed `sync/move` can leave a half-moved folder (the per-file fallback then fails and the next scan adopts the files by hash or, on MEGA, makes conflict copies). **Stale folder cache (seen on Drive, Nov 2026):** the shared `rclone rcd` keeps a path -> folder-id cache per remote, refreshed on every use (the 5-minute expiry never fires while the app is busy). A folder moved or renamed in the cloud still answered under its old path, so the echo of our own local rename (`sync_paths` on the old paths) found "cloud files" there and downloaded them again, and Sync now trashed them and did it again. `Engine::full_scan` therefore calls `Remote::forget_cache` (`fscache/clear`) before listing. **Drive shortcuts:** rclone dereferences them by default (a shortcut to a folder lists the target's files under the shortcut's path), so a shortcut was synced as a second real copy and a local delete inside it would have deleted the original. Drive logins carry `skip_shortcuts = true` (`login_params`); older logins get it at runner start (`Rclone::skip_shortcuts`, a `config/create` copy through `replace_remote`, local to rclone, an error stops the runner). The copies already on disk then read as deleted in the cloud and are trashed (the delete guard may ask first). **Old cloud folder after a move:** the moved folder's old path is a folder the user removed here, so `run_dirs` (see "Folders are synced") removes it with `remove_empty_dir` (`operations/rmdir`, which refuses a non-empty folder). Relies on each provider's rmdir refusing a folder with content we cannot see (Google Docs skipped by `skip_gdocs`): not tried on a real account; the cloud's own trash holds a removed folder.
- **Delete guard rules (`run()`, `Engine::report_stop`):** (1) `delete_guard_ok`: over 50% of the known files (small accounts: all of them). (2) `Engine::folder_wiped`: every known file of one folder of 10+ (any depth). A folder that is **gone** from disk (`symlink_metadata` says `NotFound`) is not judged: a deleted folder is the user's, a vanished drive leaves its empty mount point (known limit: a folder holding only a deleted subfolder is left empty and stops once). The `stopped` log row's path is `share` or `folder:<dir>` (the activity log words it), msg the raw line. A stop of a run of paths asks for a full scan (cause `guard`) **only if a stopped delete is a `DeleteLocal`** (`Report.aborted_local_deletes`): a folder renamed in the cloud reads that way and only a full scan pairs it; the user's own deletes (`DeleteRemote`) gain nothing from one (it cost 9 min on 21k files). Two accepted limits: a local folder rename whose old names reach a run without the new ones (split across bursts) and is over the limits now stops and asks instead of being paired by a full scan (nothing is lost); and a mount point that its own tool removes on unmount, whose parent still holds other synced files, is skipped by the folder rule (only the share rule applies; the files stay on the drive and go up again on remount, the cloud copies sit in the provider's trash). The `stopped` code `cap` = more deletes than the user confirmed. Full-scan causes in the log: `delete`/`restore` (the card's answer), `guard`, `folders` (too many folders), plus the older `decision`/`moves` on old rows.
- **Cloud duplicate = local copy (`Engine::pair_copies`, after `pair_moves`):** a `Download` of a new cloud file of at least `COPY_MIN` (1 MiB) whose bytes `same_content` proves equal to another synced local file of the same size (`Db::paths_with_size`, indexed; the candidate must still match its DB row, not be ignored or under a symlink; `PAIR_TRIES` hashes) gets that file in `Work.from` and stays a `Download`. `fetch` then runs `copy_local` (checks the source's `Sig` before and after `fs::copy`, sets the cloud's mtime) and falls back to the real download on any doubt. The source's DB row is kept (`run_transfers` forgets `from` only for moves). Logged as `down`. Tested with a remote that refuses downloads; not tried against a real account (needs a provider hash, so never MEGA). **Local duplicate = cloud copy (`Engine::pair_uploads`, after `pair_copies`):** an `Upload` of a new file (no cloud file) of at least `COPY_MIN`, not in download-only, looks at the same candidates (`paths_with_size`, still as synced) but, since the DB keeps no hash, asks the cloud live: one `stat` per candidate (`PAIR_TRIES`) for its hash, against `Remote::local_hash` of the new file (read once per hash kind). A match puts the candidate in `Work.from` (`remote` = its item); `transfer` then calls `Remote::copy` (`operations/copyfile` inside one remote: server-side on Dropbox/Drive/OneDrive, with the OneDrive "directory not found" `mkdir` retry), `stat`s the result and accepts it only if size and hash equal the candidate's (the cloud source may have changed since the check); anything else uploads (copyfile overwrites a bad copy). The source's row stays (`run_transfers` forgets `from` only for `MoveLocal`/`MoveRemote`). Logged as `up` (msg = the source path, not shown by the UI for `up`). The new cloud file's mtime is whatever the service gives a copy; the DB row stores what `stat` reports, so it reads as in sync. Tested with `Hashing` (counts uploads/copies, a copy with other bytes) and through real rclone (bytes and a clean second pass only: the `local` backend has no server-side copy); **not tried against a real account**. - **Quota on the card:** `Rclone::about` (`operations/about`, parsed by `quota`: `used`, optional `total`) is read by a thread in `main.rs` at start-up and every 15 min for every account into `State.quota`; a failed read keeps the old value, no `total` = no line. `refresh()` fills `AccountRow.quota-used|total|percent|level` (percent floored; `quota_level`: 80 % amber, 95 % red); the card shows `QuotaMeter` (a short neutral gauge, never full width or blue: those mean transfer progress; its words are passed in from `AccountCard` so they stay in its `.po` context). Not told to the user any other way (no notification, not in the tray). Untested against the real services: which of them report `total`; an account added after the pass shows its line at the next one.
- **Folders are synced, empty ones too (like the official clients).**
  - **Rule:** `decide::decide_dir` (pure, table-tested) compares local / cloud / a row in the `folders` table (`Db::dir_synced|add_dir_row|forget_dir_row|dir_rows_under|all_dir_rows`). `user_version` 2: the migration seeds it with every folder of the existing `files` rows, or an upgraded account would re-make a folder deleted here. Folders stay out of `files` so the guard's counts and every "known files" query stay about files.
  - **Planning:** `scan` also returns the folders it entered. `Engine::plan_dirs` filters them like files: unchecked, `blocked`, a case-only twin among the candidates that a side really has (left alone), a side that cannot be told = `None` (left alone, never "deleted"). A folder a rule hides: with a row it becomes a `hidden` `DirWork` (cloud copy removed empty-only, local one stays; a mirror or restore only forgets the row), without a row it costs nothing.
  - **Acting:** `run(work, dirs, report)` acts **after** `run_transfers`, removals deepest first, then creations shallowest first (`run_dirs`/`dir_action`). Not counted by the delete guard, but a guard stop, a cancel or a held account drop them with the files. A `MakeCloud` for a folder that has a file uploaded under it this run (not failed or postponed) only writes the row: uploads make their folders, so a first sync costs no extra request per folder.
  - **Removal is empty-only** (`fs::remove_dir`, `Remote::remove_empty_dir`). "Not empty" (and a file or nothing holding the name) is just forgotten: whatever is in it syncs as files, and a local folder holding only a `.DS_Store` stays and goes up again at the next scan. Any other failure (no permission; an rmdir error with the folder still there) is retried with the row kept, or the folder would come back from the side it was deleted on.
  - **A folder a run emptied is not removed** (`prune_cloud_dirs` is gone; `prune_empty` stays only for an unticked folder in `drop_excluded`): only a folder the user deleted is. `Remote::make_dir` is `operations/mkdir`; the default is an error, so a test wrapper must delegate it.
  - **Path runs:** `sync_paths_in` collects the folders of the reported paths (local walk, `dir_rows_under`, the feed listings' `is_dir` items, the folders a new rule hides) and asks the cloud about the rest through `lookup` (one listing per parent). `local_changes` reports folders without a row and rows without a folder, each at most once per `DIR_REPORT_EVERY` (30 min, `Engine.dir_reported`) so a folder that never settles does not start a run at every walk.
  - **Not done / unverified:** the case-only rename of an empty folder (left alone as a twin); no activity-log rows for folders. Untested against a real Dropbox/Drive/OneDrive/MEGA: the mkdir/rmdir answers (on Drive a folder holding only a Google Doc, hidden by `skip_gdocs`, may look empty to rmdir: try it before trusting), and whether the feeds report an empty folder's creation or deletion at all (if not, the 5-minute walk and the full scans find it).
