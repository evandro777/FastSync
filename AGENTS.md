# AGENTS.md: FastSync

Notes for AI agents and contributors. Read this before changing anything.


## What this is

A **light and fast** Linux desktop app in Rust + Slint: an Insync-style two-way folder sync for Dropbox, Google Drive, OneDrive and MEGA. Priorities: fast start, low memory, simplicity, and above all never losing the user's files. `PLAN.md` has the original design.

**Our own sync engine; rclone only moves the bytes.** `rclone rcd` runs on localhost (random password, our own `rclone.conf`, never the user's) and gives login (`config/create`), `operations/list|stat|copyfile|deletefile`. Everything else is ours:

- `decide.rs`: the pure three-way compare (local, remote, last synced) -> action; conflict names; delete guard; case-collision check. Exhaustively unit-tested. Change it only with a test for the new case.
- **Same bytes, other times:** `decide` only sees size + mtime, so `run()` turns a `Conflict` into `Adopt` when sizes match and `Remote::same_content` proves equal content. `RcloneRemote` does that with the hash the listing carries (`Item.hash`: first of md5, sha1, quickxor, dropbox, sha256; `showHash` on `list`/`stat`) against `Rclone::local_hash` (rclone hashes the local file). No hash (MEGA) = false = both copies kept. **A hash check that fails is not "different":** `Remote::compare` (default = `same_content`) returns `Err` when the call fails (`Rclone::local_hash` is a `Result`: an unreadable or vanished file, rclone busy) and `Ok(false)` for no hash; `adopt_identical` turns an `Err` into `Action::None` plus a "could not compare, will retry" error (so the normal retry runs) instead of a conflict copy of identical bytes. `pair_moves`/`pair_copies` still use the plain `same_content`: there a wrong "no" only costs a download. Tested through real rclone in `rclone_local.rs`; not yet tried against the real OneDrive/Drive/Dropbox.
- **Interrupted upload:** quitting mid-upload leaves a 0-byte item in OneDrive (the API lists it, the web hides it). `run()` turns a `Conflict` of a non-empty local file against a 0-byte cloud file into `Upload` (not in download-only). Without it the real file was renamed `(conflict …)` and the empty one downloaded over its name, again on every restart (nested `(conflict) (conflict)` names). The cause is inferred from the DB and the folder, not seen in a real cloud.
- `db.rs`: per-account SQLite (`accounts/<id>/state.db`, `PRAGMA user_version` = 1 since 0.2.0: a release that changes a table must migrate by it, `CREATE TABLE IF NOT EXISTS` adds no columns): path -> how both sides looked after the last sync, the remote ids, the remote folder ids and the delta cursor. A row is written only after its transfer succeeded.
- **Activity log:** a `log` table in the same `state.db` (`Db::log` best effort, never fails a sync; `trim_log` after every run: 30 days, 2000 rows, `LOG_DAYS`/`LOG_ROWS`). Kinds: `up`, `down`, `trash`, `delcloud`, `conflict`, `error`, `stopped` (the guard's counts line), `scan` (values only: path = `full:<cause>` (`rescan` start-up/rescan, `reset` cursor, `feed` a folder change, `now`, `decision`, `rules`, `retry`, `moves` a path run that asked for a full scan, `resume`, `tick`; the first cause of a scan wins, `runner::mark`; shown as the row's caption, an old row with plain `full` has none) or `paths`, size = ms, msg = "changed failed"; worded in the UI so it translates). Written where each action succeeds or fails in `run()`, at the listing/stat errors in `engine.rs`, and by `runner.rs` (a `scan` row when a run moved something or failed, and for every full scan except the quiet 5-minute `tick` of providers without a feed (it would add ~288 rows a day); a path run that moves nothing is not logged, so the 2-minute walk never floods it; tested through a real runner in `tests/runner_scan_cause.rs`; `Warn`/inotify errors). The UI (`crates/app/src/activity.rs`, `LogDialog`) reads it with `db::read_log`, a **read-only** connection of its own (the engine owns the only writer), on a thread; the full list stays in a thread-local and the tabs only filter it. There is no clear button on purpose. Messages stay raw, everything FastSync words (kinds, "5 min ago") is `@tr` in `Tr`; counts are adjectives ("2 changed") so no plural forms are needed. Removing an account or changing its local folder deletes the DB, and the log with it.
- `engine.rs`: `full_scan` (lists both sides; first sync, delta reset, MEGA-style providers) and `sync_paths` (only the paths from inotify or a delta). It talks to the cloud through the `Remote` trait: tests use a plain directory as the "cloud" (no rclone, no network); `rclone.rs` has the real one. The invariants (all tested): local deletes only move to `.fastsync/trash` and only for a file the DB proves we synced; downloads go to `.fastsync/tmp` then rename; a user edit during a download wins; remote names that escape the folder (`..`) are refused; a listing error (a root "not found" included, which once passed as an empty cloud) fails the run and is never read as "everything deleted", and the guard prints its counts to stderr when it trips; a run deleting more than 50% of 10+ known files stops, and so does one that deletes every known file of a top-level folder with 10+ (`Engine::folder_wiped`: an unmounted disk inside the folder stays under 50%; a delete whose local file still exists, i.e. an ignore rule, is not counted; the case-clash code lives in `engine/case.rs`) (a folder of 3 to 9 known files stops only when the run deletes all of them; under 3 is not guarded) (`Report.aborted` = deletes, known, first `engine::SAMPLE` paths; `Status::Stopped` carries the same). **A stop holds the account** until the user answers on the card: the runner saves it as JSON in DB meta `held` (`runner::Held`), runs nothing while it is set (no walk, scan or feed paths, so no "up to date" and no saved cursor; Sync now, rescans and timers are ignored; Pause/Resume re-show the Stopped card and a `Warn` does not replace it), and it survives a restart (the first status is `Stopped`). `Runner::resolve(Decision)` is the only way out: **Delete them** runs a full scan with `Engine.confirmed_deletes = Some(held deletes)`, a cap so a card that sat for days cannot approve a bigger delete than it named (a bigger plan stops again with the new count); **Restore** sets `Engine.restore`, which turns every delete of that scan into the opposite copy (`DeleteLocal` -> `Upload`, `DeleteRemote` with no local file -> `Download`, with one -> `Forget`; never in download-only, whose card offers only Delete). `held` is cleared only after that run finished without errors (after errors the decision stays and the retry carries it out). A stop is shown on the card (the paths go in `AccountRow.detail`; the "…and N more" line in `main.slint` hard-codes `SAMPLE` = 5), as `Overall::Stopped` in the tray, and once as a desktop notification (`notify.rs`, zbus `Notifications.Notify` on a thread; `State.warned` holds the accounts already announced, an `Idle` status clears it; the Flatpak needs `--talk-name=org.freedesktop.Notifications`).
- **Trash size / Empty (Settings):** `engine::trash_dir|trash_usage|empty_trash` (never follow symlinks). `trash_job` in `main.rs` counts (or empties, then counts) every account's trash on a thread; `TRASH_GEN` drops a stale answer, and `on_scan_trash` skips while `trash-busy`, because Settings re-creates itself (and calls it from `init`) right after the `EmptyTrashDialog` (opened from Settings like About, both buttons return there). A removed account's trash is no longer counted (its folder is no longer known): the removal thread runs `purge_trash` once with the current limit and leaves the rest (the Remove dialog says so). It must not delete `.fastsync/tmp` or the folder: the same folder may already belong to a new account that is writing there.
- **Trash age:** `settings.trash_days` (default 90, 0 = never, clamped to `MAX_TRASH_DAYS`). `engine::purge_trash` deletes `trash/<unix seconds>/` batches whose folder name (the time it was trashed, not the file's mtime) is old enough; non-numeric folders stay. A thread started in `main.rs` runs `purge_all` at start-up and every 6 h and reads the limit from the `TRASH_DAYS` atomic, never from the UI thread's `Settings`; changing the SpinBox saves it and runs one pass at once. Not started in fixture runs.
- **Built-in ignored names:** `engine::ignored` (case-insensitive for the native/OS names: `.dropbox*`, `.tmp.drive*`, `.debris`, `.DS_Store`, `Thumbs.db`, `Desktop.ini`, `~$*`; also `.fastsync`, `.part`, `.swp`...) is checked on the local walk, the cloud listing (`safe_rel`) and inotify (`runner::rel`), so such a name is invisible on both sides. Not a user rule on purpose.
- **Ignore rules:** `ignore.rs` (`Rules::parse|matches`, own small gitignore matcher; no `ignore`/`globset` crate, they pull `regex`) reads `<root>/rules.fastsyncignore` (`RULES`, never ignored itself, synced like any file). `Engine.ignore` is consulted first in `run()`: a synced file (DB row + cloud copy) that now matches gets `DeleteRemote` (the Dropbox way: cloud copy goes, local stays, counted by the delete guard), a row without a cloud copy or in download-only gets `Forget`, anything else is skipped; `skippable` keeps ignored never-synced paths out of `sync_paths`/`local_changes`. `scan(root, skip, ignore)` does not enter a folder `Rules::matches_dir` hides (nor does `sync_paths` for a folder event inside one), so a path missing from its result must be read as "ignored", never "deleted": `run` applies the rules before anything else, and `local_changes` filters the DB rows with `ignore.matches` for the same reason (without it every walk would call them deleted). `runner.rs` re-reads the file every loop turn and folds its text into `excluded_key`, so a change forces a full scan the same way a picker change does. Change `ignore.rs` only with a test.
- **Download only:** `Account.download_only` -> `Engine.download_only` makes `run()` use `decide::decide_down` (never `Upload`/`DeleteRemote`; `exec` refuses them too). A local edit or local-only file goes to the trash, the cloud copy wins. The delete guard's `known` is then max(DB rows, local files in the run), because a new account has no rows. The flag travels Add/Edit dialog -> `Picker.download_only` -> `apply_folders`, which restarts the runner when it changes.
- **Looking up changed paths (`engine::lookup`, used by `sync_paths`):** one `stat` per file cost 30-60+ s for 84 new files (before any transfer started). The paths are grouped by parent folder; a folder with more changed files than its listing has pages (`Db::count_in` / 1000 + 1) gets one non-recursive `Remote::list_dir` (`operations/list`, paths from the fs root, checked through real rclone), the rest is `stat`; all of it `PARALLEL` at a time. A listing error falls back to `stat` per file. A "not found" listing counts as "the folder is gone" (every path `None`) **only** when `stat` of the folder itself also says gone (one extra request; it is what keeps 84 deleted files from costing 84 `stat`s), never for the root; anything else falls back to `stat` per file, so a listing glitch is never read as a cloud delete. The trait default for `list_dir` is an error, so a test remote without it just uses `stat`. A listing matches names exactly, `stat` on Drive/OneDrive is case-insensitive: not tried against a real account. **Names that differ only by case (`Engine::settle_case_clashes`, rules in `decide::resolve_case_group`, tested on facts alone), in `full_scan` and in `sync_paths_in` (`case_siblings`: one `read_dir` per folder finds namesakes the watcher did not mention):** Dropbox and OneDrive take them for one file, so, as Dropbox's own client does (checked by the owner): (1) **a rename by case alone** (`MyFile.txt` -> `myfile.txt`: the old name has a DB row and no local file, the new one is a new local file) is a rename, never a clash: both names go through the plan, the new one is read as having no cloud copy (`Settled.renames`; a case-insensitive cloud answers for it with the old file, which used to be adopted while the old name became a cloud delete of the only copy), `pair_moves` pairs them and `MoveRemote` does `Remote::rename` (`movefile`). **The new name only counts as "no cloud copy of its own" when the cloud's answer for it is the old file** (`is_old_file`: same `id`, else another spelling, else same size and time): a cloud that allows both names (Drive) may already hold another device's file under the new one, and moving onto it would overwrite it (that is then an ordinary conflict). `case_siblings` also asks the DB (`Db::paths_ci`, one lookup per changed path through the expression index `files_lpath` on `lower(path)`, added with `CREATE INDEX IF NOT EXISTS`: no table changed, so no `user_version` bump; SQLite's `lower` is ASCII-only, so a non-ASCII-only case difference is found only from the disk listing or when the old name is also reported), so a watcher run that reports only the new name still finds the old one and looks at both. `MoveRemote` skips its "appeared in the cloud" check only for that same file, and **never falls back to upload + delete** (on a case-insensitive cloud the upload lands on the old file and the delete removes the only copy): when the direct `rename` fails it goes **through a temporary name** (`rename_by_case`: `to` + `CASE_TMP`, two renames, a failed second one is undone), and only if that fails too is it an error, retried. **A folder renamed by case alone** (`Docs` -> `docs`) cannot be done file by file (the cloud answers for `docs/a.txt` with the file in `Docs`): `move_dirs` treats a case-only group as a folder move even for one file, checks the temporary name is free and does `move_dir_by_case` (two `move_dir`s). **Every case-only rename is checked, whatever it answered** (`spelling_kept`: the cloud's own non-recursive `list_dir` of the parent must show exactly the new spelling, `stat` may echo the asked-for one; a remote without `list_dir` is accepted unchecked): a direct rename that said "ok" and changed nothing goes on through the temporary name, and one that still does not show the new spelling is an error with no DB row written (a row would make the pair a name clash at every later full scan). A case-only move of a file whose **folder part** differs (the folder was renamed but `move_dirs` could not move it whole, e.g. an unknown file in the cloud folder) is a clear error, never a per-file move. A crash between the two steps leaves a `….fastsync-case-tmp` name in the cloud (a folder of it is downloaded and the local one uploaded again at the next scan: slow, nothing lost). Unverified on Dropbox/OneDrive: whether even the two-step rename changes the stored spelling; (2) **a second, new file** is renamed locally to `myfile (Case Conflict).txt` (`decide::case_conflict_name`, `Engine::plan_case_conflict` picks the name, `case_renames` holds the plan, `apply_case_renames` renames **inside `run`, after the delete guard and the cancel checks** (a stopped run leaves the user's files alone; one that changed meanwhile stays and its upload is dropped); regular files only, never over an existing or planned name, logged as kind `conflict` and added to `Report.conflicts`, so the user is told) and goes up as a file of its own; the oldest keeps its name when none was synced; (3) two names that were **both** synced before, a mirror (never renamed), or a file that cannot be renamed are `Report::skip`ped as before. `lookup` answers `CLASH_WHY` for a path whose cloud folder listing holds only another spelling, or whose `stat` returns an item with another spelling; `sync_paths_in` then makes the Case Conflict rename. **Not done:** the same by case alone in the **cloud** (cloud `MyFile.txt` -> `myfile.txt`): `full_scan` leaves the two names alone as a clash, a path run may download a second local copy. **Unverified:** that rclone's `movefile` renames by case alone on Dropbox/OneDrive (rclone has special handling for case-insensitive remotes, not tried: until verified the rename may show the error above, nothing is lost), and whether rclone's `operations/stat` returns the stored spelling or the requested one on Dropbox/Drive/OneDrive; if it echoes the request, a lone new `report.txt` beside a cloud-only `Report.txt` is not caught by the `stat` path (only by the listing path, or the next full scan).
- **Which paths a run looks at (`Engine::paths_to_sync`):** inotify paths pass `filter_local` (a path whose local file equals its DB row is the echo of our own write); paths from the cloud's feed never do (a cloud edit or delete leaves the local copy untouched, so the filter dropped it and the cursor then moved past the change). `runner.rs` keeps the two in `pending` and `feed_paths`. **Also in `run`/`full_scan`:** two cloud files with one name (Drive) are skipped with an error, like a case clash; an upload of a path the plan saw no cloud file for first `stat`s it and refuses if one appeared; `Engine::trash` never replaces an earlier trashed copy of the same path (`.1`, `.2` suffix); the folder check rejects `..` and judges symlinks by their target.
- **Parallel transfers:** `run()` does deletes, conflicts and DB-only actions one at a time first, then `run_transfers` runs the uploads and downloads `PARALLEL` (4) at a time on scoped threads. Workers call the free fn `transfer` (no DB, so `Remote` is `Send + Sync`); every DB write, log row and counter stays on the run's thread (one SQLite connection). `Progress` shows the file that started last, `done` counts finished ones. Download temp names carry a counter. A cloud's 429s are rclone's to retry; lower `PARALLEL` if a provider complains. `Rclone::list` deserializes straight into `Entry` (a listing that does not parse is an error, never a shorter list).
- **First scan of a big cloud (100k+ files on Dropbox sat 11+ min on "Checking for changes…", measured: rclone idle on one open connection, 0 DB rows, so the time is the one recursive `operations/list`):** `RcloneRemote::list_progress` (`Remote::list_progress`, default = `list`) is `walk_cloud` (a free fn over a `list_one` closure, unit-tested with a fake cloud) and works a queue of folders `PARALLEL` at a time: the top `SPLIT_DEPTH` (3) levels one level per call (their subfolders join the queue, so the total grows), deeper folders as one recursive call each (splitting only the top level left the two biggest folders as two long calls stuck at "24 of 26"); it reports folders done/found; any failed part fails the whole listing, and two same-named sibling folders (Drive) fall back to the single `list()`. `Progress.phase` (`Phase::ListCloud|ScanLocal|Compare`, default `Transfer`) is set by `full_scan` and `run` (also the Adopt-only stretch of the exec loop); `runner::ticker` sends non-transfer phases too and fills `Progress.secs` (the clock; no rclone call). `main.rs::live` maps them to `AccountRow.transfer` 4/5/6 with the clock in `speed`. `Engine::adopt_identical` runs the equal-size `same_content` hash checks (each reads a whole local file) `PARALLEL` at a time after the planning loop. **Not measured on the real Dropbox:** whether the split listing is faster than one call (Dropbox may throttle; one huge top-level folder gains nothing) and where the 11 min went; the listing has no percentage, only folders done and the clock.
- **Pause/Stop end a run in progress:** the worker reads its events only between runs, so `Runner::pause(true)` and `stop()` also set `Engine.cancel` (shared `Arc<AtomicBool>`) at once. `run()` checks it before the guard (a cut-short plan is never judged), before each one-at-a-time action, and `run_transfers`/`adopt_identical` workers before each job: transfers under way finish, none starts; `Report.cancelled` is set and the runner `continue`s without saving a cursor, the `excluded` key, a `held` decision or an "up to date" status; a cut-off full scan sets `full` so resuming scans everything, a cut-off run of some paths puts those paths back in `feed_paths` (`ran`) instead, so resuming costs no listing. An idle Pause (no run cut short) does not: `Pause(false)` only sets `walk`, and the feed/inotify paths queued meanwhile are synced (`pending`/`feed_paths` survive the paused `continue`), so a resume costs no cloud listing. Only the worker's `Event::Pause(false)` clears the flag (never before a run, or a Pause pressed as a run starts would be lost). The cloud lookup of `sync_paths` (`lookup`) and the move/copy pairing loops check it too. **`runner::EndRun`** (drop guard) raises the ticker's `over` flag even when the run panics: `thread::scope` joins the ticker before it lets a panic out, so without it a panic (now catchable, no `panic = "abort"`) hung the worker for good. `runner::clean(&Report)` (no errors but skips, no guard stop, not cancelled) is the test for "may this run confirm the `excluded` key or a held decision"; the feed cursor has the looser `Retry::may_confirm` (see the retry paragraph). Timers (`timer`) sleep one whole interval, no per-second wake-ups, and end at the first tick after the worker is gone. A listing stops between folders (`Remote::list_progress(.., cancelled)` fails with "cancelled", never a partial list; `full_scan` then returns `cancelled`, not an error, and also checks after the local walk and every 256 paths of the plan); the rclone call under way finishes. `panic = "abort"` is **not** set in the release profile: it would make the runner's `catch_unwind` (one account's panic = an error card, not a dead app) do nothing.
- **Symlinks:** `scan` never lists a link, and nothing is read or written under a symlinked folder (`under_symlink`, `refuse`); `run()` plans nothing for a path with no listed local file where `symlink_metadata` finds something (a link holds the name), or the download failed on every retry, no run was ever clean and the feed cursor was never saved (a full scan at every start). The official Dropbox client syncs a link as an **empty file whose target is only in the file's metadata** (`symlink_info.target`; rclone does not pass it on, `Rclone::list` hashes show the empty-content hash). `make_link` (in the transfer workers, before `transfer`) handles a planned `Download` of a new 0-byte file with no local file and no `from`: `Remote::link_target` (`RcloneRemote`: Dropbox only, one `files/get_metadata` through `delta::dropbox_link_target` with rclone's token) and, if it is a link whose target passes `safe_link_target` (relative, ≤4096 bytes, never above the root by names alone), `symlink()` (fails if the name exists). **No DB row** (`Done::Link`): `local_sig` cannot describe a link, and a row would read as "deleted here" later; the next scan is stable only through the planning check above. An unsafe target is `Done::Skipped` (no error, not logged, retried at each scan); a failed lookup is an error (retried), so a glitch never makes an empty file. Local links are never uploaded (the API has no way to create one: the `symlink_info` field is in `FileMetadata` responses only). Costs one metadata request per new empty Dropbox file (every `__init__.py` of a first sync). Not tried against the real Dropbox end to end (only the field's shape, read through the API); a link deleted here comes back at the next scan; a cloud delete of the entry leaves the local link; team-space accounts may need a path-root header; a relative target through another link can still leave the folder (only names are checked).
- **Providers without a feed (MEGA):** the 5-minute timer sends `Event::Tick`, not `Full`; `scan_due` drops a tick when the last full scan ended less than `SCAN_EVERY / 2` ago, because ticks pile up behind a long run and a listing slower than the interval would otherwise restart the moment it ended. `scan(root, skip)` does not enter unchecked folders. A **new** download is linked into place with `hard_link` (fails if the name exists; falls back to `rename` where hard links fail), so a file saved since the check is never replaced; an overwrite of a file we synced still uses `rename`. `Rclone::speed` has a 5 s limit (`send_within`), the only timed call: the ticker runs inside the run's thread scope. `trash.rs` holds the trash functions (re-exported from `engine`). `main.rs::clashes` compares the accounts' folders by their real paths too (a symlink to another account's folder).
- **The account cards' model is long-lived:** `main.rs::refresh` keeps one `Rc<VecModel<AccountRow>>` (`ROWS`) and `sync_rows` changes only the rows that differ, because a running sync reports once a second and a new model each time recreated every card (a click or a text selection spanning that moment was lost). Fixtures set their own model and do not exercise this path. `emblem::set` runs `gio` on a thread of its own (it is called from the sync worker, and `gio` can wait long on the metadata service).
- `delta.rs`: `RemoteChanges` per provider (Dropbox cursor + long poll, Drive `changes.list`, OneDrive `/delta`) with JSON parsing split from HTTP so it is tested on canned answers. Drive/OneDrive report ids, so `impact()` turns them into paths with the folder ids the DB keeps; a folder created, moved or renamed there triggers a full scan because its children's paths change unreported. **Dropbox reports paths:** a new or moved folder entry (also the echo of a folder FastSync itself uploaded into) goes into `Impact.dirs`, which the runner keeps in `feed_dirs` and hands to `Engine::sync_paths_in(paths, dirs)`: one recursive `Remote::list_under` per top folder (`feed_dirs_to_list` drops reported subfolders; `list_folders` lists `PARALLEL` at a time; more than `FEED_DIRS_MAX` = 30 sets `Report.wants_full` and the runner runs a full scan instead, nothing touched) (after `forget_cache`; its items answer for their paths, so no `stat`), not a listing of the whole cloud (10+ min on 100k files). A folder that cannot be listed is a failure of its own (`Report::failed_dirs`, `Report::fail_dir`; kept in `Retry.dirs` and listed again alone, never a full scan, and the cursor may move on); "not found" for it is "gone" only when `engine::folder_gone` agrees (also used by `lookup`: not the root, and the folder's own `stat` says gone). Only a batch of `SPLIT_MOVE_MIN` (50) deletions forces a full scan now (a folder renamed in the cloud can arrive as its deletions first; a smaller split move costs a trash and a re-download). Drive/OneDrive still scan for any folder change (they report ids; untried). Expired cursors (`Poll::Reset`) trigger a full scan and a new cursor.
- `runner.rs`: one worker thread per account owns the engine and DB, fed through one channel by the inotify watcher (debounced), the delta poller and timers (a local walk: the event ticks every minute (`WALK_TICK`) and `walk_due` decides, from the Preferences settings `walk_minutes` (default 5, with a working inotify watcher) or `walk_fallback_minutes` (default 2, when the watcher failed to start or `WATCH_LIMIT_HIT` is set), both 1 to `MAX_WALK_MINUTES` (60) and read from the `WALK_MINUTES`/`WALK_FALLBACK_MINUTES` atomics so a change applies at once; a full scan every 5 min without a feed; a retry after errors, waiting 1, 2, 4, 8, 16, then 30 minutes while runs keep failing: `retry_after`). **A failed file is retried by itself, not by a full scan (`Retry`; a listing of a big cloud took 10+ min on a 100k-file Dropbox, during which nothing else syncs):** `Report` tells the errors apart: `fail(path, why)` (one action on one path failed: `log_failed`, `adopt_identical`'s "could not compare", a `sync_paths` lookup; a move's old path too) goes to `Report.failed`, `skip` (a name clash or two cloud files with one name: state, only `full_scan` checks them, so a path retry would bypass the check and must never run them) is shown and never retried, and whatever is pushed straight into `errors` is global (`has_global_failure`: the cloud listing, the state DB, `drop_excluded`) and needs a full scan. `Retry` keeps `paths` (`failed` + `later`) and `dirs` (`failed_dirs`), together at most `RETRY_PATHS_MAX` = 5000, then a full scan, `full`, the `retry_after` back-off, and writes `[full, paths]` (`[full, paths, dirs]` when a folder failed; both load) as JSON to DB meta `retry` (`Retry::save`, only when it changed) **before** the feed cursor is saved, so a restart retries just those paths (`Retry::load`: due at once; an unreadable value means a full scan). `take_due` gives `Due::Paths` (they join `feed_paths`, never `filter_local`) or `Due::Full`; `record(report, ran, did_full)` removes the paths a run looked at, adds its failures, and a clean full scan replaces everything. **`Retry::persist` does both writes in the one order that is safe (the failed paths, then the cursor, and the cursor only if the first worked and `may_confirm`; tested with a DB that refuses the `retry` key). The cursor (`Retry::may_confirm`) is saved unless the run was stopped, cancelled, had a global failure, or a full retry is waiting:** path failures no longer hold it, which is what made every restart scan the whole cloud. `clean(&Report)` (no errors except `skip`s, which are states: a permanent clash must not keep anything from being confirmed; no stop; not cancelled) stays strict for the `excluded` key and a held decision, and a held decision is only cleared by a clean **full** scan (`Retry::escalate` (through `Retry::finish_run`) makes the retry a full one while a decision is pending, since a failed path does not carry it out). The unchecked-folders/rules key uses the looser `runner::settled` (a whole scan, no stop, not cut short, no global failure; failures of single files do not hold it, they are retried by path, and a folder that could not be trashed is a global error), or one stuck file cost a listing at every restart. `after_cancel` says what a cut-short run leaves (a full scan starts over, a run of paths re-queues its paths and `feed_dirs`). The cursor is also held back when `Retry::save` could not write the `retry` value. **A file that changed under its transfer is not an error:** `transfer` turns an upload failure (rclone's "corrupted on transfer" hash check on a file saved meanwhile) into `CHANGED` when `local_sig` differs from the plan, and `fetch` does the same for a download; `run_transfers` puts the path in `Report.later` (no log row, no red card, retried in 60 s, then 2, 4 ... 30 min while it keeps changing (`later_fails`, apart from real failures: a database or VM image that never stops would otherwise be uploaded in part every minute; inotify events for it still start a run each, a per-path cooldown for that is not done), and the edit's own inotify event normally syncs it first). The feed poll's `Warn` goes out only from the third failure in a row (a 429 or a blip is no Problem row); its wait is 30 s doubling to 10 min and never shorter than the service asked (`Retry-After` header, copied into the body by `delta::finish`, or Dropbox's `error.retry_after`; `fail` writes `(retry after N s)`, `delta::retry_hint` reads it back; an HTTP-date value gives no hint). The feed's recovery after a failed poll sends `Event::Recovered` (a walk to clear the old message), not `Event::Full`: its cursor did not move, nothing was missed. The retry timer's wake-up is `Event::Retry` (it used to be `Full`). Still a full scan: first sync, no cursor, a cursor `Reset`, a changed unchecked-folders list or rules file, a held decision, Sync now, a global failure. Unit-tested (`Retry` is pure); not tried against the real Dropbox. A panic in the worker is caught in `spawn` and shown as an error status. Pause, Sync now, Resolve (the answer to a stopped run), Stop are events. When inotify runs out of watches (at start-up, or later through the watcher callback's `MaxFilesWatch` error) the runner sets `runner::WATCH_LIMIT_HIT`; `on_scan_trash` (every opening of Settings) turns it into `watch-fix`, the sysctl command Preferences shows (`watch_fix_command`). Only a restart clears it. The 2-minute walk only shows "Syncing" when it finds paths. **Conflict alert:** `Report.conflicts` (paths) is collected by the runner; every run that leaves any pending pushes `alert_at` to now + `CONFLICT_QUIET` (10 s), and the top of the loop calls the second `spawn` callback `on_conflicts(count, first path)` once it is due (not part of `Status`, so no card/tray change; `main.rs` words it from `Tr` and sends it critical through `notify.rs`). A restart drops unannounced ones (they stay in the log). **Notification clicks:** `notify::send(summary, body, actions, on_action)` always declares a `default` action and keeps the handler by the id `Notify` returned (`HANDLERS`, dropped on `NotificationClosed`); `listen` subscribes to `ActionInvoked`/`NotificationClosed` once, before the first `Notify`, on the kept `BUS` connection. A click on the conflict alert raises the window and opens the log on Problems; one conflict adds a `show` button (`show_file` in `main.rs`: `FileManager1.ShowItems` with `file_uri`, else `xdg-open` of the folder, which is also what the Flatpak gets); the stop alert's click only raises the window. A conflict row in the log (`LogRow.path`, kind 4 only) has the same folder button (`log-show-file`). Unverified in a live desktop: that Cinnamon's notification server reports a click on the body (`default`) and on the button, and that Nemo selects the file. The timer path is untested (needs a real conflict through `spawn`); only `Report.conflicts` has a unit test.
- Embedded OAuth client: `rclone.rs::embedded_client` bakes the project's own Google/Dropbox/OneDrive client ID at build time (`option_env!` of `FASTSYNC_{GOOGLE,DROPBOX,ONEDRIVE}_CLIENT_{ID,SECRET}`, from the repo secrets `{GOOGLE,DROPBOX,ONEDRIVE}_CLIENT_{ID,SECRET}`, mapped in `appimage.yml` and `flatpak.yml`; `flatpak/build.sh` hands them to the sandbox through the gitignored `flatpak/embedded.env`). The user's own ID wins; unset (local builds, forks) means rclone's shared ID. The secret is readable in the binary.
- **rclone is restarted when it dies:** `Rclone::send_within` retries a failed call once after `revive`, which starts `rclone rcd` again on the same port and password (so every runner's `Arc<Rclone>` keeps working); `restarts` tells "restarted since" from "same process, other failure", `closed` (set by `shutdown`) keeps a quit from bringing it back. `engine/pair.rs` holds `pair_moves`, `pair_copies` and `adopt_identical` (their tests stay in `engine.rs`, with the fixtures). The emblem `gio` calls go through one ordered queue thread.
- Tokens: delta clients read the access token from rclone's config (`Rclone::token` first makes rclone refresh it when close to expiry).
- The synced tree is always the cloud's **root**: there is no `remote_path` (selective sync replaced it).
- **Rename/move detection (`Engine::pair_moves`, called in `run()` before the delete guard counts, so a rename is never a delete):** a `DeleteLocal` (DB row, local copy untouched) is paired with a `Download` of the same size, and a `DeleteRemote` (cloud copy, no local file) with an `Upload`, when `Remote::same_content` proves equal bytes (the listing's hash against `Rclone::local_hash`). **No hash (MEGA):** the pair also counts when the file **name is kept** and the new side's size and mtime are exactly the old row's (`Base.local` for an upload, `Base.remote` for a download), the only proof there is (a different file with the same name, size and mtime would be wrongly moved; the name is required because archives and `rsync -t` give whole batches one size and time; providers with a hash never use this). So on MEGA a folder rename or a move to another folder pairs, a rename of one file does not. Candidates must share the file name or the parent folder, same-name first, `PAIR_TRIES` hashes per new path (sequential, on the run's thread). The pair becomes `Action::MoveLocal` (`fs::rename`, checks the old file is unchanged and the target absent) or `MoveRemote` (`Remote::rename` = `operations/movefile`; checks the cloud copy and that the target is free; if the move fails it uploads and deletes the old, as the unpaired plan would), run in `run_transfers` with the new `Work.from` (`Moved`: the old path). The new DB row is written first, then the old one forgotten. Never `MoveRemote` in download-only (`refuse`). Log kind `move` (path = new, msg = old path; kind 8 in `activity.rs`, `is_file`). Tested with `DirRemote` and through real rclone (`rclone_local.rs`); `movefile` is not tried against Dropbox/Drive/OneDrive. A rename split over two runs (two inotify bursts) falls back to upload + delete. **Folder move (`Engine::move_dirs`, just before `run_transfers`):** the `MoveRemote` jobs are grouped by the folders left once the common ending of old and new path is cut off (`dir_pair`: `a/x/f` -> `b/x/f` is `a` -> `b`); a group of 2+ files becomes one `Remote::move_dir` (`sync/move` of folder onto folder, `Rclone::movedir`, which rclone does with the service's own `DirMove` where there is one) only when `dir_move_proven`: neither folder excluded, `Db::under(old)` has exactly the group's files (no other synced file moves along), the unfiltered `Remote::list_under(old)` holds exactly those files with the synced sizes/times (nothing another device added, nothing ignored or hidden), `stat(new)` is `None` (a move onto an existing folder merges), and the new local files are as planned. Then `forget_cache`, `list_under(new)` and a row per file (size must match; with a good listing a file it does not show stays a one-by-one job, which fails its own `cloud_unchanged` and is sorted out next run; with a failed listing every file gets its row from what the old row knew, since a move keeps size and time). Any failed proof or call leaves the per-file moves. Tested through `DirRemote` (`Counting`) and real rclone's `local` backend (folder inode kept); **not tried against Dropbox/Drive/OneDrive**: whether their `DirMove` is used through `rcd`, and whether a failed `sync/move` can leave a half-moved folder (the per-file fallback then fails and the next scan adopts the files by hash or, on MEGA, makes conflict copies). **Stale folder cache (seen on Drive, Nov 2026):** the shared `rclone rcd` keeps a path -> folder-id cache per remote, refreshed on every use (the 5-minute expiry never fires while the app is busy). A folder moved or renamed in the cloud still answered under its old path, so the echo of our own local rename (`sync_paths` on the old paths) found "cloud files" there and downloaded them again, and Sync now trashed them and did it again. `Engine::full_scan` therefore calls `Remote::forget_cache` (`fscache/clear`) before listing. **Drive shortcuts:** rclone dereferences them by default (a shortcut to a folder lists the target's files under the shortcut's path), so a shortcut was synced as a second real copy and a local delete inside it would have deleted the original. Drive logins carry `skip_shortcuts = true` (`login_params`); older logins get it at runner start (`Rclone::skip_shortcuts`, a `config/create` copy through `replace_remote`, local to rclone, an error stops the runner). The copies already on disk then read as deleted in the cloud and are trashed (the delete guard may ask first). **Empty cloud folders:** after a run, `prune_cloud_dirs` calls `Remote::remove_empty_dir` (`operations/rmdir`, which refuses a non-empty folder) for every ancestor of the cloud paths this run deleted (`DeleteRemote`) or moved away (`MoveRemote`), deepest first, never the root or an unchecked folder; its errors are ignored (they mean "not empty"). Relies on each provider's rmdir refusing a folder with content we cannot see (Google Docs skipped by `skip_gdocs`): not tried on a real account; the cloud's own trash holds a removed folder.
- **Cloud duplicate = local copy (`Engine::pair_copies`, after `pair_moves`):** a `Download` of a new cloud file of at least `COPY_MIN` (1 MiB) whose bytes `same_content` proves equal to another synced local file of the same size (`Db::paths_with_size`, indexed; the candidate must still match its DB row, not be ignored or under a symlink; `PAIR_TRIES` hashes) gets that file in `Work.from` and stays a `Download`. `fetch` then runs `copy_local` (checks the source's `Sig` before and after `fs::copy`, sets the cloud's mtime) and falls back to the real download on any doubt. The source's DB row is kept (`run_transfers` forgets `from` only for moves). Logged as `down`. Tested with a remote that refuses downloads; not tried against a real account (needs a provider hash, so never MEGA). **Local duplicate = cloud copy (`Engine::pair_uploads`, after `pair_copies`):** an `Upload` of a new file (no cloud file) of at least `COPY_MIN`, not in download-only, looks at the same candidates (`paths_with_size`, still as synced) but, since the DB keeps no hash, asks the cloud live: one `stat` per candidate (`PAIR_TRIES`) for its hash, against `Remote::local_hash` of the new file (read once per hash kind). A match puts the candidate in `Work.from` (`remote` = its item); `transfer` then calls `Remote::copy` (`operations/copyfile` inside one remote: server-side on Dropbox/Drive/OneDrive, with the OneDrive "directory not found" `mkdir` retry), `stat`s the result and accepts it only if size and hash equal the candidate's (the cloud source may have changed since the check); anything else uploads (copyfile overwrites a bad copy). The source's row stays (`run_transfers` forgets `from` only for `MoveLocal`/`MoveRemote`). Logged as `up` (msg = the source path, not shown by the UI for `up`). The new cloud file's mtime is whatever the service gives a copy; the DB row stores what `stat` reports, so it reads as in sync. Tested with `Hashing` (counts uploads/copies, a copy with other bytes) and through real rclone (bytes and a clean second pass only: the `local` backend has no server-side copy); **not tried against a real account**. No hash (MEGA) = never.
- **Quota on the card:** `Rclone::about` (`operations/about`, parsed by `quota`: `used`, optional `total`) is read by a thread in `main.rs` at start-up and every 15 min for every account into `State.quota`; a failed read keeps the old value, no `total` = no line. `refresh()` fills `AccountRow.quota-used|total|percent|level` (percent floored; `quota_level`: 80 % amber, 95 % red); the card shows `QuotaMeter` (a short neutral gauge, never full width or blue: those mean transfer progress; its words are passed in from `AccountCard` so they stay in its `.po` context). Not told to the user any other way (no notification, not in the tray). Untested against the real services: which of them report `total`; an account added after the pass shows its line at the next one.
- No empty folders, no on-demand files: see the README.

## Architecture decisions (inherited from FastMoji, measured there)

- **Software renderer only** (`winit` + `software`, forced in `main.rs` and in `Cargo.toml` features with `default-features = false`): ~27 MB RSS versus ~108 MB with the GL renderer.
- No async runtime. Scans/work in threads, results handed to the UI thread with `slint::invoke_from_event_loop`.
- Never hold a `RefCell` borrow while calling something that makes Slint re-read a model.
- Keep dependencies few and light.
- **Wrapped text in a dialog = `HintText` (or `SelectableText`) with `avail: root.text-avail`, never a bare `Text { wrap: word-wrap }`.** Slint reports a wrapped `Text` as one line high whatever its width, so the layout, and with it a `ScrollView`'s scrollable height, comes out short and the last field cannot be reached (this broke the Edit dialog repeatedly, each time a note was added or a translation got longer). The components estimate their height from the width. Never patch a `ScrollView` with a hand-tuned px "slack"; its `preferred-height`/`content-height` is just the layout's. To check, render the dialog at a small height and scroll is not capturable, so render a tall one (see Look) and look for cut or missing fields, in English and `pt_BR`.
- Slint notes: a `VerticalLayout` inside a `ScrollView` needs `alignment: start`, or a short list spreads its rows over the window; read-only `TextInput` (one per block) makes text selectable; use `content-y` (not `viewport-y`); a callback named `close` shadows a builtin (use `dismiss`); `FocusScope.capture-key-pressed` intercepts keys before `LineEdit`; a wrapped read-only `TextInput` in a nested layout reports one line of height, so give it room with `min-height`, estimated from the available width (a fixed character count leaves a blank band under lines that still fit on one line); `Text` and `TextInput` have no `padding`, so put the space in the parent layout's `spacing` or `padding`.

## Look

- Native Fluent widgets on purpose: apps follow the system accent and light/dark mode. In Slint 1.18 the `Palette` colours are read-only; only `Palette.color-scheme` can be set (the Appearance setting does that). To change a colour you would have to write your own component.
- One page: a header (icon, title, Add account, burger) over a scrolling list of `AccountCard`s (`AccountRow` struct: state 0 up to date, 1 syncing, 2 paused, 3 problem, 4 stopped by the delete guard). A `.po` context is the component name: `Main`, `AccountCard`, `AddDialog`, `FoldersDialog`, `ShareDialog`, `RemoveDialog`, `SettingsDialog`, `About`, `AboutCard`, `Tr`. A row property called `row` clashes with a built-in Slint property: the card's is `acct`.
- A problem's text is the raw message from rclone, the OS or the provider (not translated); everything FastSync words itself is in `@tr()`.
- Snapshots are 600x520 (the default window) and cannot scroll, so a list taller than that is only partly visible. To see all of it, render with a taller window: put `height = 800` in a `settings.toml` under a scratch `XDG_DATA_HOME` and run the script with that variable set.
- `LANGUAGE` (often `en_US` on a dev machine) beats `LANG`: to check a translation run the script with `LC_ALL=pt_BR.UTF-8 LANGUAGE=`.

## Dialogs

- **Closing the window hides it to the tray** (`on_close_requested` returns `HideWindow`, the loop is `run_event_loop_until_quit`): syncing must go on. Without a tray host the close button quits instead, or the app would be unreachable. Quit (tray menu) calls `quit()`, which also kills rclone: statics are never dropped, so the child would otherwise outlive the app. This replaces the Fast family rule "closing Main always ends the app".
- Dialogs are in-window overlays (the last children of `Main`), not second windows, and `scripts/ui-snapshot.sh` can capture them (`FASTSYNC_PAGE=add|add-mega|settings|about`). The Add account dialog runs the browser login on a thread (it blocks until the user finishes); `login_gen` makes a cancelled login discard its token. They share one shell, `component Dialog` (dim background, Esc, Tab trap, card capped to the window height); a new dialog inherits it and puts its content inside. **Selective sync:** Add and Edit share one flow, `AddDialog` then `FoldersDialog`. Add logs in, lists the root folders (that listing is the connection check; a failure deletes the token again), saves the account **paused** and opens the picker; its Save unpauses and starts it, its Cancel leaves it paused (`on_toggle_pause` starts a runner when Resume finds none). Edit lists the folders of the existing login; the service is not editable, the login is: there is no login button: Save (**Next**) calls `Rclone::reauth` when needed, which logs in under a temporary remote `<id>x`, checks it by listing the root, asks `proceed` (the `login_gen` of a cancel) and only then copies all its settings over the real remote with `config/create` (rclone replaces an existing remote as a whole, so an old client ID cannot linger; its "Token already configured - replace it?" question is answered no in `answer()`, or it would open the browser again), then `fscache/clear` and lists the real remote too; if that fails (a setting that did not survive the copy, MEGA's obscured password being the one to watch) the old settings are put back, so a failure leaves the old login. **MEGA gotcha:** rclone keeps a logged-in MEGA session per email and reuses it for any remote with that email without checking the password, so a listing through the running `rcd` passes with a wrong or empty password (this once replaced a working login with an empty one); `mega_login_works` therefore logs in for real in a fresh `rclone` process, with the credentials in environment variables. After it the runner gets `rescan()` (a held account ignores it, so a login for another cloud cannot confirm a stopped deletion). That re-authentication (`reauth(ui, then)` in `main.rs`, then `begin_edit`) runs first when the Client ID/secret fields differ from the saved login (`State.edit_client`; a token belongs to its client), when a MEGA password was typed, or when the folder listing fails with an auth error (`login_expired`: invalid_grant, 401 and the like, never network errors; once per Save, `begin_edit`'s `renew` flag). An auth error we do not recognise just shows the error; changing the client fields forces a login. The fields are prefilled from `config/get` (MEGA's email, a client ID that is not the built-in one: `is_embedded_client`). A login for a *different* cloud account is not detected: the DB would read it as remote deletes, which the delete guard and the trash soften. The picker's state is the `PICKER` thread-local in `main.rs` (UI thread only; threads hand results over with `upgrade_in_event_loop`); it is a flat row list, children are listed one level at a time when a row is expanded. A row shows its arrow only after `probe` found folders inside it (one `list_dirs` per listed folder, four worker threads; a failed probe counts as "yes"), so a level of N folders costs N rclone calls. `Account.excluded` holds the unchecked folders; the engine (`excluded`, `toggle_excluded`, `drop_excluded`) skips them on both sides, and unchecking a synced folder trashes its local copy (never the cloud copy; a locally edited file stays) and forgets the DB rows. Saving stops the old runner and **waits** for it (`Runner::stop_and_wait`: two engines must never share a DB); a changed local folder deletes `accounts/<id>` (the DB) so the new folder is merged, not read as "everything deleted". `SettingsDialog` (burger button in the header) holds Appearance and Language plus an About button; `About` opens from it and closing About returns to Settings (re-creating Settings gives its keys focus back, so Esc keeps working). The About version comes from `CARGO_PKG_VERSION`, the Website button opens `CARGO_PKG_REPOSITORY` with `xdg-open`. A `ScrollView` does not report its content's height, hence the explicit `preferred-height` in the settings card.
- Theme and language are saved the moment they change (`theme-changed` / `language-changed`, skipped when the value equals the stored one so start-up never writes); window size only on a normal exit. An unknown locale falls back to the English source strings (`select_language` in `main.rs`).

## Translations

- UI strings use `@tr()`; strings built in Rust go through the `Tr` global in `ui/main.slint`. Never `format!` user-visible text in Rust.
- `.po` files are generated by `dev/gen_po.py` (edit its table, run it, commit both). Slint's gettext context is the component name (`Main`, `Tr`). A new `@tr` string needs an entry in every language. A string with a count needs its own singular string for `n == 1` ("1 connection", not "1 connections"), with its own entry.
- Language = `settings.language` (`""` = system locale).
- Appearance = `settings.theme` (`""` = follow the system, `"light"`, `"dark"`). The Appearance box sets `Palette.color-scheme` in the `.slint` (`unknown` hands it back to the desktop). `THEMES` and `theme_index` in `crates/app/src/main.rs` keep the order of that list, and a test checks they agree. `Family.dark` reads the drawn background, so it stays right in every state.

## GitHub flow and releases

Work on branches, PRs to `master`. CI: `ci.yml` (fmt, clippy, tests, MSRV, metainfo/desktop validation), `appimage.yml` (AppImage on every push/PR; on a `v*` tag it attaches to the release), `flatpak.yml` (bundle on every push/PR; on a `v*` tag it also publishes the signed remote and the landing page to GitHub Pages, then attaches the bundle), `virustotal.yml` (scans the AppImage and the Flatpak after their workflows; needs the `VIRUSTOTAL_API_KEY` secret). `RELEASING.md` has the one-time setup and the steps. Never commit or push on the owner's behalf.

Release gotchas (each one broke a first release):

- Bump the version in `Cargo.toml`, then run `cargo check` and commit `Cargo.lock`: CI uses `--locked`, so a stale lock fails every job.
- The metainfo needs a `<release version="X">` for the tag, or `flatpak.yml` fails.
- `appimagetool` builds `.DirIcon` from a PNG at the AppDir root, not from the SVG. The icon must follow `docs/ICON-STYLE.md` (the same tile shape for every Fast app, flat colors only). Regenerate `packaging/io.github.evandro777.FastSync.png` when the SVG changes: `convert -background none -density 384 packaging/io.github.evandro777.FastSync.svg -resize 256x256 packaging/io.github.evandro777.FastSync.png`.
- The first tag needs the one-time setup in `RELEASING.md`: the signing key and its secret, Pages, and the `v*` tag rule on the `github-pages` environment.

## Flatpak

App id `io.github.evandro777.FastSync`; `flatpak/build.sh --devel` installs `...FastSync.Devel` next to a release. Needs `flatpak-builder` and `org.freedesktop.Sdk//25.08` + `org.freedesktop.Sdk.Extension.rust-stable//25.08`. The runtime version `25.08` appears in five places (the manifest, the container image tag, the rust-stable install and its `GITHUB_PATH` line in `flatpak.yml`, and the header of `flatpak/build.sh`): bump them together.

- Auto-update = our own signed OSTree remote on GitHub Pages (`flatpak.yml`: `bundle` → `pages` → `release`), deployed on `v*` tags only. Every deploy replaces the whole site, so never deploy Pages from another trigger. The public key is `flatpak/signing-key.b64` (base64 of the binary export, made by `flatpak/new-signing-key.sh`; the template ships none); the private half is the secret `FLATPAK_GPG_PRIVATE_KEY`. See `docs/FLATPAK-SIGNING.md`.
- Keep `finish-args` minimal (the manifest says how for X11-only apps and trays). The build vendors crates (`cargo vendor`), so `flatpak/vendor` must not be in the manifest's `skip:`.
- Patterns to copy when an app needs them (FastClipboard has each one working): inside the sandbox `FLATPAK_ID` is set. A single-instance Unix socket must live in `$XDG_RUNTIME_DIR/app/$FLATPAK_ID/`, the only directory shared between `flatpak run`s. A ksni tray needs `.disable_dbus_name(true)` there. Start at login must go through the Background portal (`org.freedesktop.portal.Background.RequestBackground`, blocking, so from a thread), not a file in `~/.config`. A host command (for example `tesseract`) is reachable only through `flatpak-spawn --host`, which needs the user's own opt-in `flatpak override --talk-name=org.freedesktop.Flatpak`: never put that in the manifest.
- **Flathub policy:** manifests must NOT contain AI-generated content and AI must not open the submission PR. Do not write a Flathub manifest or submission text for the owner; `docs/FLATHUB.md` explains the process.

## Open items

- Nemo submenu (`nemo.rs`): the actions "Copy share link" (`fastsync --share <file>`) and "View on web" (`--web <file>`) are grouped in a "FastSync" submenu through the user's `~/.config/nemo/actions-tree.json` (uuid of an action = its file name; the submenu's is `fastsync-menu`). `merge_tree` only adds/refreshes our submenu, takes our actions out of every other place, keeps everything else, leaves a file that is not a layout alone, and the first change to an existing file keeps `actions-tree.json.fastsync.bak`. The submenu's `user-icon` is the app icon by theme name (`io.github.evandro777.FastSync`, installed by `nemo::install_icon` into the user's hicolor theme like the emblems); only a `null` icon is filled in, so a user's choice stays. Unverified in a live Nemo: that Nemo takes the submenu without a restart and shows the label "FastSync". "View on web" (`core/web.rs`): Dropbox builds the URL, Drive uses `open?id=<ID>`, OneDrive asks Graph for `webUrl` (`delta::onedrive_web_url`), MEGA opens `fm/<parent handle>`; the ids come from `Rclone::stat` (`ID` is always in rclone's listing JSON); any failure opens the provider's home. None of the web URLs was tried against a real account. No provider documents a URL that opens its Share window, so there is no "Share…" item.
- Share links: a running copy gets `share <path>` / `web <path>` over the instance socket (so `MAX_COMMAND` in `instance.rs` is now 4200: copy that file to the other Fast apps), a fresh start handles it after loading the accounts. `accounts::locate` maps the path to account + cloud path, `Rclone::public_link` calls `operations/publiclink`, `SHARE_GEN` drops a slow answer for an older file. The action files are written by `nemo::install` from `refresh()` (so it follows the account list; `Files=*<root>/*;` per account limits it to the synced folders (the leading `*` is the only glob form Nemo's docs promise to match against the full path). An action file needs `Extensions` or `Mimetypes` or Nemo rejects it with a warning (`nemo --debug` shows it): ours has `Extensions=any;`, which matches files and folders; `any;dir;` matched folders only (tried in a live Nemo 6.6: `any` is special only as the sole value), the file is removed with no accounts) using `$APPIMAGE` or `current_exe` (a dev binary rewrites it to the dev path) and skipped in the Flatpak. A root with `*?[];\` is left out. Unverified in a live Nemo: that the leading-`*` glob matches files in subfolders, and whether Nemo picks up a changed action file without `nemo -q`. Untested against real services: Dropbox needs the `sharing.write` scope (in `docs/OWN-CLIENT-ID.md`; the embedded client and tokens issued before it need checking), a file the sync has not uploaded yet is told apart only by rclone's "not found" text.

Written without a live cloud account, so these are **untested against the real services**: the OAuth question flow of `Rclone::login` (follows the documented non-interactive protocol: answers `config_is_local` with true, every other question with its default), the three delta clients' HTTP (only their JSON parsing is tested), token refresh, delta latency, cursor expiry, the extra `stat` before an upload over an existing cloud file (a provider whose list and `stat` times differ by more than 2 s would make it fail every time), and four transfers at once against real rate limits. `rclone_local.rs` and `runner_guard.rs` run through a real rclone's `local`/`alias` backends and are skipped without rclone. Test each by hand before trusting it.

- A folder picker for the *local* folder of the Add/Edit dialog (it is typed in). The cloud-side picker exists (selective sync) but is untested against real services: `list_dirs` assumes rclone's `operations/list` with `dirsOnly` returns `Path` relative to the fs root; check it by hand.
- Selective sync: saving stops the old runner, which now ends its run at the next file or folder (`Runner::stop` raises `Engine.cancel`), so Save waits only for the calls under way; and `drop_excluded` trashes the local copy without checking that the cloud still has it (the files stay recoverable in `.fastsync/trash`, which nothing empties). The runner stores the unchecked list of its last clean full scan in DB meta `excluded` and forces a full scan when it differs.
- Selective sync: an unchecked folder under a Drive/OneDrive folder that is later renamed in the cloud shows up as a new, checked folder (the list is by path).
- Status emblem (`emblem.rs`, `gio set metadata::emblems`) uses our own badges (`crates/app/emblems/*.svg`, copied at start-up to `$XDG_DATA_HOME/icons/hicolor/scalable/emblems/emblem-fastsync-*.svg`, never removed) and the setting `file_emblems`. It is on the local root folder only, set from the runner's status callback and cleared on quit/remove; it is skipped inside the Flatpak (gio would write the sandbox's metadata). Per-file emblems would need a Nemo extension plus a socket to the app. Untested in a live file manager.
- Transfer detail on the card: `Engine.progress` (`engine::Progress`: file, kind, done/total, set by `run()` before each `exec`, reset at the end; adopt/forget count as done but name no file) is read once a second by `runner::ticker`, which also asks `Rclone::speed` (`core/stats` for the group = account id; `copyfile` sends `_group`) and sends `Status::Syncing(Progress, speed)` only when it changed. `main.rs::live` turns it into the `AccountRow` fields. Untested against a real rclone: that `core/stats {"group"}` reports `speed` for a running `copyfile`. No ETA, no per-file byte percentage, not in the tray tooltip.
- Start at login (Background portal), FastSync's own verified OAuth client ids (users can already enter theirs: `docs/OWN-CLIENT-ID.md`; an own-id login is untested against rclone 1.76's extra "shared client_id" question, answered by `answer()` in `rclone.rs`), Google Docs export, MEGA's push channel.
- OneDrive work/school accounts with an own app need tenant-specific `auth_url`/`token_url` (rclone docs); not set by FastSync yet.
- `rclone rcd` is killed on a normal quit; after a SIGKILL of the app it is left running (it only listens on localhost with a random password). `PR_SET_PDEATHSIG` would fix it.
- Browser login: the blocking `config/create|update` steps run as rclone jobs (`call_job`, `_async` + `job/status`), and `cancel_login` (Cancel/dismiss, and the start of every `login`) does `job/stop`. Without it an abandoned login kept the auth server on port 53682 until rclone's own timeout and the next one failed with "failed to start auth webserver: … address already in use" (reproduced in a scratch network namespace; `job/stop` frees the port). A login started in another process (a terminal `rclone config`) can still hold the port.
